# 第三题参赛匹配度与竞争力复核

核查日期：2026-10-17。依据用户提供的赛题正文、项目已归档官网摘录、当前源码及验证产物，并查阅 Nexent、Jev 官方说明和相关研究。只新增评估文档，不修改业务代码、不启用模型、不上传仓库。

后续同步说明：本轮源码、配置、测试、证据和文档随本次仓库提交纳入版本管理。下文“未跟踪、未上传”描述为评估当时状态；远端同步以实际 Git 提交与推送记录为准。真实模型 API 仍关闭。

## 判断

**政务方向符合第三题，工程闭环已经形成，但尚不能认定核心任务全部达标。工程完成度明显强于算法创新与真实业务验证。**

现在最值得展示的是：将原文与正式要求分开管理、按分支与环节核验、更新时暂停冲突、分项复核发布，以及历史可追溯。最大缺口是低资源本体半自动构建和演化、真实跨文档推理、真实资产价值验证、新流程在 Nexent 中实际由模型调度。

建议项目定位为：**面向低标注政务资料的证据约束知识演化与办事决策追溯智能体**。群众咨询作为展示窗口，资料认知、本体演化和决策影响才是技术主线。

## 三个容易被误认成完成的部分

**自然语言提问不等于已实现问题理解。** 当前新工作流保存问题文本，正式清单主要由用户选择的 facts 与 branch_id 决定。任意政务问题的意图识别、跨事项路由、自由问题驱动的检索仍未完成。应明确称为“结构化办事情境咨询”。

**知识更新不等于本体演化。** 当前修改的是固定要求的动作、出处及同义项。本体层要能提出和复核新的类型、关系或约束，并处理旧实例的兼容、迁移和查询行为，才覆盖本题这一核心要求。

**工程验收不等于业务效果。** 现有 352 项回归、21 项模拟闭环、16 项实际接线检查有价值。本轮核对了对应 9 个源文件的指纹，均与验证记录一致；没有重复跑完整测试。它们不证明真实问答准确率、Jev 中文分类质量、构图效率或获奖概率。

## 已有创新点怎样表述

| 机制 | 能说明的贡献 | 不能夸大的部分 |
| --- | --- | --- |
| 材料实体与具体提供要求分离 | 同一旧卡可在申请时交验、领取时交回；按分支、环节、动作、条件分别管理，减少混淆 | 是领域建模与应用设计贡献，尚无证据证明是新知识表示算法 |
| 原文资料层与正式业务知识层分开 | 新原文可查，未经确认的要求不进确定清单 | 是可信工程机制；要用错误确定项和复核耗时对照证明收益 |
| 当前暂停状态独立于历史版本 | 来源变化后暂停受影响要求，分项复核后恢复；历史答案或回退不能绕过当前冲突 | 目前变化目标由固定模拟包指定，不能宣称已经自动发现所有语义影响 |
| 三值条件核验及逐项出处 | 条件未知不默认满足或不满足；每条结果绑定规则、关系和原文 | 三值逻辑与证据追溯本身已有先例，优势应落在政务任务上的实际错误减少 |
| 模型角色与程序发布权限分开 | 模型可提出候选，程序校验，专业人员发布 | 当前真实模型尚未接入，不能宣称多 Agent 已优于单 Agent |

Jev 适合做分类与原文支持判断的辅助信号，但不是赛题强制组件。使用它不是独立算法创新，也不能替代图谱和复杂推理。其官方说明强调原子、结构化判断，复杂问题应拆解后由程序组合。[Jev 官方说明](https://docs.typesafe.ai/introduction)

## 与已有方法比较

以下是查阅公开原始资料后的判断，不是完整查新，也没有复现对方实验。

- GraphRAG 已把知识图谱与原始片段结合用于回答，“图谱＋检索”不能直接称首创。[官方查询说明](https://microsoft.github.io/graphrag/query/overview/)
- LightRAG 已结合图结构、向量和增量更新，“向量＋图谱＋定时更新”不能单独构成新算法。[论文](https://arxiv.org/abs/2410.05779)
- iText2KG 已研究零样本增量实体、关系构建，AutoSchemaKG 已研究模式归纳。仅说“LLM 少标注构图、自动生成关系”还不够。[iText2KG](https://arxiv.org/abs/2409.03284)、[AutoSchemaKG](https://arxiv.org/abs/2505.23628)
- Nexent 本身提供工具、Skills、多模型、知识检索、追溯和版本管理等能力，不能把平台现成功能算作团队原创。[Nexent 官方仓库](https://github.com/ModelEngine-Group/nexent)

现阶段可以主张“面向政务变化的可核验工程闭环”，不宜主张“首创可进化多智能体算法”。如果要形成算法贡献，建议聚焦**固定专家预算下的候选复核排序＋证据依赖影响分析**：用冲突风险、证据缺口、影响业务范围决定先复核什么，再只重核受变化影响的知识与结论。这是待实现、待对照的研究方向。

“低资源”应体现少量标注、少量专家时间或有限领域知识。4B/8B 和单卡说明部署资源成本，不能单独证明低资源本体构建有效。

## 竞争力判断与补强

这是工程判断，不是官方给分，也没有足够证据评价其他参赛队伍的实际水平。

| 方面 | 当前判断 | 最有效的补强 |
| --- | --- | --- |
| 场景清晰、展示可理解 | 较强 | 用一个真实事项讲清申请/领取和条件例外 |
| 系统完整、变化可控、可追溯 | 较强的工程基础 | 演示正文改变→影响项暂停→专业复核→局部恢复→旧版可查 |
| 算法创新、低资源本体 | 较弱，属于主要失分风险 | 做种子引导候选构建、复核优先级、结构演化与影响传播实验 |
| 真实业务价值 | 较弱，尚无独立效果证据 | 同资料同任务下比较人工、普通 RAG、增强方案的耗时和错误 |
| 平台深度集成 | 接线较完整，真实调度未证实 | 最后启用 API 后，记录主 Agent→子 Agent→工具的实际轨迹 |
| 复用与开源交付 | 有模板基础，迁移与交付未验收 | 第二事项/地区只换配置、数据；提交完整文件，在干净环境复现 |

优先做一个能看见“资料变成价值”的闭环：旧办事指南、材料表和补充通知共同支持一个有例外的办理问题；单份资料不足以得到答案。随后受控模拟其中一条通知改变，系统展示受影响项目、暂停与分项恢复。真实来源与模拟变更分别标注，不伪造官方政策变化。

补齐三组证据，再谈强竞争力：

1. **少量种子能否省专家时间**：相同标注与专家分钟预算，对照人工/无约束模型、种子约束普通复核、所提排序；测每专家分钟正确采纳的类型/关系/约束数及错误发布数。
2. **多文档推理是否有收益**：同源资料、同模型、独立留出任务，对照普通 RAG、关系＋原文、加入条件/版本/门控的方案；测错误确定项、遗漏项、出处支持、恰当待核实和耗时。
3. **增量演化是否可靠且划算**：对照全量重建与按依赖重核；测影响精确率/召回率、更新成本、旧版回放和遗漏影响。再换第二个事项验证模板复用，记录代码与配置改动量。

评测题及其改写按同一原始案例分组留出，先由独立复核形成答案。现有评测模板的 cases 为空，不能据此声称业务准确率。小库 29% 查询提速属于工程优化，不是本体创新实证。

## 当前交付建议

保留主架构，开发重心转到真实资产、本体候选和可比较效果，暂不增加更多 Agent 或扩展多个行业。API 按既定要求留到最后；在接入前把候选结构、真实公开数据模式、证据映射和独立评测准备好，不能用 synthetic 标签绕过真实资料边界。

技术证据：[流程优化说明](Agent流程核查与优化-2026-10-17.md)、[接线边界](先接线后启用API.md)、`evidence/agent-workflow/optimization-verification.json`、`evidence/knowledge-heartbeat/parser-verification.json`。开源前还须把当前未跟踪的新源码与配置纳入提交，并核对赛事模板、模型/工具说明、数据清单和干净环境复现；本轮没有执行上传。
