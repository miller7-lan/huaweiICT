## 判断

**政务方向与赛题匹配；现有实现主要完成平台接入、受控调用和资料处理基础，尚未覆盖赛题的核心业务闭环。工程验证已有证据，算法创新尚未建立可审查的成果。**

保持现有技术底座，后续主线应聚焦“少量专家投入下的本体构建与演化，以及演化对业务决策的影响”。仅继续完善群众问答和工作人员材料核对，覆盖面仍不足。当前不预测官方分数或获奖概率，也不把需求条目计数换算成精确匹配百分比。

## 创新性：已知技术与项目贡献的边界

本次检索四项代表性原始资料，核对官方方法介绍或论文摘要。没有复现其性能，也没有进行穷尽式文献检索。只能据此判断泛化创新声明缺乏充分依据，不能认定某个具体待实现方法必然没有新意。

| 代表性工作 | 已公开的相关能力 | 对本项目创新叙述的限制 |
| --- | --- | --- |
| Microsoft GraphRAG | Local Search 将知识图谱信息与原始文档片段共同用于回答 | “图谱＋文档检索”这一组合本身已有先例。[官方查询文档](https://microsoft.github.io/graphrag/query/overview/) |
| LightRAG，2024，后续修订 2025 | 图结构与向量结合、两层检索，并提出新数据增量更新 | “图谱＋向量＋增量更新”不能直接作为首创方法。[论文](https://arxiv.org/abs/2410.05779) |
| iText2KG，2024 | 利用 LLM 零样本、增量抽取实体与关系并构建图谱 | “低标注 LLM 增量构图”已有相关方案，需要具体方法或领域约束差异。[论文](https://arxiv.org/abs/2409.03284) |
| AutoSchemaKG，2025 | 从文本抽取三元组并归纳模式，不依赖预定义模式 | “自动发现概念和关系类型”已有研究；其动态模式归纳不能直接等同于本项目所需的业务本体持续版本演化。[论文](https://arxiv.org/abs/2505.23628) |

项目目前使用现成模型和 OCR，向量排序采用余弦相似度；这些是正常工程选型。本体种子是手工设计，当前不存在已实现的独有抽取、学习或更新算法。

群众/工作人员职责、身份核定、空证据停止、人工复核、版本固定和审计，有助于构建可用系统；其中已实现的部分可以作为工程贡献，但没有对照就不能声称它们构成新的多智能体协同算法。只有主 Agent 路由到一个子 Agent 的记录，也不能证明非空业务交接已完成。

“低资源”在本题本体环节应落实为标注量、专家投入或可用领域知识有限。使用小模型或单卡，可以说明部署成本，不能单独证明本体构建效率优势。

## 建议的创新主线

建议定位为：**面向低标注政务资产的证据约束本体演化与决策影响追溯**。这是待实现、待实验验证的项目方向，尚不能作为已经获得的创新成果。

将方法具体化为三个可检验环节：

1. **证据约束候选构建与复核排序**：少量人工种子引导候选类型、关系和约束；每个候选带原文定位。根据规范冲突、缺少支持的关系、受影响任务数量和已估计的复核成本排序。在固定专家分钟预算下，比较正确采纳的本体项目数和错误发布数。避免仅依赖未经校准的模型自报置信度。
2. **本体与业务规则的变化传播**：区分新增实例、规则值变化、类型/关系/约束结构变化；从来源片段传播到本体、规则和已有任务，仅更新受影响范围，同时保留旧版本结果。需要报告遗漏影响和错误影响，不只展示“发现文件变了”。
3. **有依据的决策回放与人工确认**：每条结论绑定原件、图边、条件和各版本；来源不足、冲突或适用范围不明时明确停止。改变一条规则后，显示哪些办理结论改变、为什么改变、哪些旧结果仍按旧版本保留。

其中本体构建的复核效率及变更传播方法应承担主要算法贡献；可审查的决策回放与 Skills 则承担业务和工程贡献。三项分别已有相关技术思路，差异必须通过具体设计与实验建立。

数据入口可以通用，但创新实验必须有明确的业务对象、专家标准和错误成本。用户已允许前期事项暂不定；因此先用模拟资料验证工程路径合理，进入业务评测前应选择真正需要跨资料判断、有条件分支、有规范依据及可核验版本变化的场景。答案全在一份短指南中的任务，不足以支撑多跳与演化的效果声明。

## 需要怎样证明

| 实验 | 对照设计 | 应报告的指标 |
| --- | --- | --- |
| 本体构建 | 无约束 LLM 候选；种子约束＋普通复核顺序；种子约束＋所提排序 | 类型/关系/约束正确性、候选采纳率、每专家分钟正确采纳数、标注量和模型调用量 |
| 多文档推理 | 普通向量 RAG；图谱＋文档的基础方法；加入来源/条件/版本约束的方法 | 结论支持率、有效引用定位率、图路径支持率、无依据停止与错误停止情况 |
| 演化处理 | 全量重建；所提受影响范围更新；移除结构变化检查的版本 | 影响识别精确率/召回率、更新时间和调用成本、旧版回放一致性、遗漏变更数 |
| 工程协同 | 单 Agent 与分工方案，在同一任务与工具权限下比较 | 任务完成、错误引用、越权/无依据调用、工具次数、耗时；不预设多 Agent 必然更好 |
| 业务复用 | 相同引擎在第二套资料上只更换允许的配置 | 修改范围、迁移人工时间、复现成功率与质量损失；换文件但改大量逻辑应如实记录 |

同模型、同源资料、同任务组和同人工预算；将案例及其改写作为一组留出。先建立独立人工答案，再设置合理目标。现在 cases=[]，因此没有可计算的业务准确率，也不能把此前空库技术对照结果当成本体或多跳效果。

## 优先落地顺序

1. 在独立环境接通已准备的解析资产、非空检索 MCP 和一个真实业务 Skill；保留原空库保护。
2. 完成本体候选生成→约束检查→人工复核→发布的最小闭环；区分本体模式与图谱实例。
3. 实现一个跨文档、带条件与逐步证据的任务，端到端在 Nexent 中运行。
4. 做一次可核验的版本变化，贯通影响任务与旧版回放；模拟变化清楚标注，真实政策变化另验。
5. 完成上述对照和方法消融，再整理创新声明与正式材料。

建议将原计划“文字业务闭环稳定后再评估多模态”调整为首个赛题闭环就覆盖小规模三模态、本体候选及至少一项规范映射。M2/M3 可保留隔离和工程阶段命名，但比赛演示必须覆盖完整核心链路。新报告不替代团队业务核定，也不标记任何未实现方法为完成。
