# 政务 Agent 架构规划：问答决策记录

日期：2026-10-17。通过分轮提问确定细节。本文件记录设计决策，尚未据此修改运行配置或接入模型 API。

## 已有约束

- API 接入先留空，角色与接口契约可以先设计。
- 政务事项和资料可替换，具体事项名称后续选择。
- 正式业务知识经维护者确认后发布；日常群众咨询使用已确认规则。
- 保留原文来源、定位、知识版本及历史追溯。

## 第一轮：业务范围（用户已确定）

| 问题 | 决定 |
| --- | --- |
| 第一版业务闭环 | 群众咨询 → 系统直接提供带出处的辅助回答 |
| 回答深度 | 根据已确认规则，结合用户条件列出材料、步骤和待确认项 |
| 首版验证范围 | 一个地区、一个事项，流程跑通后扩展；具体事项待定 |

设计含义：群众咨询无需逐次等待工作人员确认答案；正式规则的发布仍由维护者确认。系统输出限于辅助办事信息，未确认适用关系保持待确认状态。

## 第二轮：查询执行方式（用户已确定）

| 问题 | 决定 |
| --- | --- |
| 查询侧分工 | 主 Agent 组织回答，检索 Agent 找证据，核验 Agent 检查条件 |
| 用户条件收集 | 先展示不同情况的分支，让用户选择自己的情况 |
| 规则不足或来源冲突 | 回答能够确认的部分，同时列出待核实项和相关出处 |

设计含义：分支选择是首选交互方式；后续仍需确定分支层级，以及缺少选项、用户无法确定时的处理。核验 Agent 核对所选条件与证据的对应关系。未解决的冲突不转化为确定业务要求。

## 第三轮：分支与条件结构（用户已确定）

| 问题 | 决定 |
| --- | --- |
| 分支展示 | 逐层选择，只展示当前相关选项 |
| 办理环节 | 分别记录申请、受理、领取等环节，各自关联条件、材料和步骤 |
| 条件不清楚或分支未覆盖 | 先保留条件未知，展示仍能确认的内容并说明缺口；随后提供可选追问入口 |

第三项用户原话为“1后面再提供追问选项”。当前交互解释：先呈现已确认部分及未知条件，再显示“补充情况”选项；用户选择后进入必要条件追问，补充信息后重新核验。用户未补充前不将未知视为满足或不满足；未覆盖分支不套用相近分支。

## 第四轮：知识表示与条件核验（用户已确定）

| 问题 | 决定 |
| --- | --- |
| 材料和提供要求 | 材料实体复用，每条提供要求分别绑定分支、环节、动作和出处 |
| 条件判定 | 模型整理条件，核验 Agent 调用程序按结构化规则计算满足、不满足、未知，再解释结果 |
| 同义与实体合并 | 系统提出建议，维护者确认后统一关联，保留原名和出处 |

设计含义：材料与材料提供要求是不同对象；同名材料不意味着提供动作、适用条件或环节相同。模型不以自由补写替代结构化判定；无法表示或缺少证据的条件应保留未知。实体合并须记录确认过程，并保留各来源中的原始名称与定位。

## 第五轮：检索与推理协作（用户已确定）

| 问题 | 决定 |
| --- | --- |
| 查询顺序 | 先按事项、分支和环节查已确认关系，同时检索原文核对；缺少关系时可补找资料，但不直接形成确定要求 |
| 补查机制 | 自动补查缺失依据，总计最多 3 轮；仍不足时展示已确认部分和待核实项 |
| 答案展示 | 先显示按环节整理的清单，每项可展开查看适用条件、依据路径、原文和版本 |

轮次口径：一轮为一次检索加核验，最多 3 轮包含首次检索。追加检索限已登记资料。需要用户补充情况时进入可选追问入口，不把重复检索当作补齐用户条件。查询固定使用请求开始时的知识版本，展示的依据路径为可复查的条件、规则和证据关联。

## 第六轮：更新影响、复核发布与规范适用（用户已确定）

| 问题 | 决定 |
| --- | --- |
| 更新与冲突 | 未受变化影响的内容沿用；有冲突的交专业人员核对处理；暂停与展示按第七轮执行 |
| 复核与发布 | 按一次来源更新形成变更包；冲突项待核实，其余依赖完整的通过项成组发布 |
| 适用性未确认资料 | 允许在依据区展示原文明示事实，同时标注适用性待核实；不加入确定办事清单 |

用户对第一项的原话：“未更新的默认按原来的沿用，有冲突的转到专业人员核对处理，未及时处理的按可能过时，暂不提供标记”。“未更新”按未发生变化且未受关联变化影响的内容理解；沿用仍遵守原有适用条件与有效时间。暂停时点、对外提示和截止时间在第七轮进一步确定。历史答案保留当时的原文、版本和判定，不能将旧记录直接作为当前仍可办理的保证。

资料原文明示事实与当前业务适用关系分别存储和展示；出处存在不代表适用关系已确认。变更包发布时须检查所引用的本体、实体和规则依赖完整，不发布依赖于未解决冲突的结论。

## 第七轮：冲突复核细节（用户已确定）

| 问题 | 决定 |
| --- | --- |
| 对外提示 | 使用用户指定文案：“工作人员正在更新相关政策，暂不提供服务” |
| 暂停时点 | 发现冲突后立即暂停受影响旧要求，等待专业人员确认；其他未受影响内容继续提供 |
| 处理期限 | 由专业人员为每个变更包指定处理截止时间 |

设计含义：暂停范围按受影响的规则及依赖结论确定，不默认停用整个事项或平台。对暂停项统一展示指定提示；其中“更新”指本系统政策资料维护与核验，不用此提示证明发文机关正在修订政策。复核期限与机器任务执行预算分别管理；未指定截止时间时记录待指定，不擅自设置 24/48 小时期限或判断超时。超过截止时间后继续暂停，专业人员核对通过并完成发布后才能恢复。

## 第八轮：维护职责、本体启动与验收（用户已确定）

| 问题 | 决定 |
| --- | --- |
| 专业人员与发布职责 | 同一专业人员角色完成核对并确认发布，分别留存核对与发布记录 |
| 本体启动 | 人工给少量类别、关系和示例，模型据此整理候选并提出扩展建议；新增或修改仍需人工确认 |
| 首版验收 | 先完成模拟资料的工程验收，真实业务核对与独立验收放在后续阶段 |

本轮没有选择“首版准备 10–20 个专业人员核对的真实业务案例”；该推荐选项不列入首版承诺。模拟流程中的专业人员操作为工程验证，不冒充真实政策复核。

后续确定具体地区、事项、真实来源、专业人员账号及接入 API；真实业务质量阈值和独立验收题在真实资料阶段确定。模型服务地址、密钥及外部服务接入继续留空。具体数据库产品、模型供应方和页面样式可在实施时选择，不改变已确认的业务规则。
