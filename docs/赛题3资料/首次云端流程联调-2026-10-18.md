## 本轮修复的接线问题

1. Docker 和工作台在检查时均未启动。启动 Docker Desktop，恢复既有容器，启动本机 8780 工作台；未重置、删除数据或重建模型。
2. DeepSeek 主机适配器也曾强制直连，现改为遵循现有环境代理；本机 Nexent API 客户端继续直连。
3. Nexent 配置、运行容器没有代理变量。使用 [compose.cloud-proxy.yml](../../compose.cloud-proxy.yml) 加载现有代理，并将主机回环地址映射为 Docker 可达的 `host.docker.internal`；代理端口不写死在业务源码中，本机及容器内服务加入 `NO_PROXY`。只重建这两个服务，验证原存储目录并复用既有镜像。
4. 模型注册需要租户管理员权限，新增云模型必须通过真实健康检查才会被平台视为可用。本轮登记 `deepseek-flash`，完成检查后绑定现有 6 个草稿；未启用或发布任何草稿。绑定脚本现先检查草稿边界，保留已验证模型的配置，未检查模型明确报 `NATIVE_MODEL_HEALTHCHECK_REQUIRED`。
5. 新模型首次原生输出是未执行的工具调用标记。它有 final 事件但没有实际工具轨迹，本轮将该次判为失败，未把流结束当作业务成功。
6. 第二次原生执行暴露轻量沙箱禁止 `import json`；后续模型自行改写又误传任务编号。保留沙箱权限，改为使用已有工具返回值：逐步读取实际任务 ID、调用子 Agent、核对持久化状态、原样返回程序回执，不新增通用导入、网络或凭据读取权限。
7. 模型上下文登记为 16,384 tokens、最大输出仍为 1,024，容纳工具定义和必要上下文；三个查询草稿更新为无需导入的调试说明。检索、核验各最多 3 步，主控最多 6 步。

本轮原生 `/agent/run` 共 3 次：前 2 次失败并保留记录，第 3 次通过。前一轮纯 Jev 单次接入不计入本轮。没有为了刷新时间或源码指纹重复通过的真实场景。

## 如何重复这条最小原生咨询

前提：当前工作台、Nexent、代理可用，现有云模型通过检查，`.runtime/agent-workflow/native-drafts.json` 有绑定信息。该入口不是从空机器部署整个项目的脚本。

```powershell
.\.venv\Scripts\python.exe scripts/verify_first_cloud_native.py --live
```

该命令会核对并更新当前三个禁用、未发布查询草稿的调试说明，拒绝覆盖已启用/已发布 Agent，然后发起一条固定模拟原生咨询。没有 `--live` 则不调用；只有真实工具、两个子 Agent 的工具轨迹及原样持久化结果齐全才通过，模型自称成功不能通过。

容器普通重启保留当前代理配置。重新部署时应同时加载 `compose.cloud-proxy.yml`，从当前进程的 HTTP(S)_PROXY 派生 Docker 可达地址并设置 `ICT_CLOUD_HTTP_PROXY`、`ICT_CLOUD_HTTPS_PROXY`；沿用既有部署的 env、镜像及数据目录，不把主机的 `127.0.0.1` 代理地址直接传入容器。
