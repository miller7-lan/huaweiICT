## 怎样打开这条流程

本机工作台：[http://127.0.0.1:8771](http://127.0.0.1:8771)。M2 MCP使用8770，独立原生运行容器使用5018；原/M1仍保留各自入口。

1. 使用本机受控群众测试账号登录，点击“建立演示任务”。不要输入真实身份证号码、照片或申请人信息。
2. 点击“运行群众Agent，检索官方依据”，查看原文位置、版本和待复核提示。
3. 选择两个模拟材料存在状态，点击“保存声明并交接”，记录实际交接号。
4. 退出后用受控工作人员测试账号登录，刷新队列，运行工作人员Agent核验最新交接。
5. 查看演示缺项、未知项及业务复核待办，勾选演示确认后保存。

当前页面的原生工作人员按钮只核验最新一条交接；API支持明确handoff_id。多任务选择页面属于后续扩展，不能把当前按钮当作任意历史交接的选择器。

工程预览的原文检索采用分类过滤及字符片段匹配，不是已验证的语义向量检索或正式业务问答准确率。它优先证明数据、引用、版本、交接和两端真实调用的完整链路。

## 启动与复现

以下命令只操作独立M2目录和服务。先完成原平台与本机私有账号配置，确认8770、8771、5018没有被其他服务占用。

```powershell
.\.venv\Scripts\python.exe scripts\prepare_m2.py
docker compose -f compose.m2.yml -p gov-m2 up -d --build
.\.venv\Scripts\python.exe scripts\prepare_m2_runtime.py
docker compose -f .runtime/m2/native-runtime/compose.json -p gov-m2-runtime up -d
.\.venv\Scripts\python.exe scripts\provision_m2.py
.\.venv\Scripts\python.exe -m gov_mcp.m2_workbench --runtime .runtime/m2
```

最后一条命令持续运行工作台。`provision_m2.py --refresh`只重发独立M2 Agent，原/M1 Agent不重发。复查使用：

```powershell
.\.venv\Scripts\python.exe -m pytest -q --junitxml=evidence/m2/regression-tests.xml
.\.venv\Scripts\python.exe scripts\audit_m1_completion.py
.\.venv\Scripts\python.exe scripts\audit_m2_minimal_flow.py
```

最后一个审计需要这台机器已经实际完成页面流程并保存截图/轨迹，不能直接把他人机器上的历史PASS当作本机新执行结果。

当前 `prepare_m2.py`读取首批私有归档 `.runtime/data-discovery/2026-10-13/ID-LAW-01.html` 和 `ID-GUIDE-01.html`，核对公开来源清单里的实际SHA-256。换机器时要通过正常公开访问自行取得原件并验证，私有目录、账号、服务令牌和平台ID不随仓库分发。网页已变化时重新登记实际来源快照，不关闭指纹校验或伪造旧文件。原始官方链接及访问限制见 [RAG资料准备](RAG资料与评测准备-2026-10-13.md)。

## 分类从第一批开始

数据库中的source/chunk/task/handoff/review对象分开保存；source带原件指纹、地区、文种、适用条件及日期标签，chunk带原文位置、材料类别、事项和版本。事项目前只有一个内部演示ID，不把它写成官方事项编码。分类索引支持地区、事项、类别和版本检索。

完整分类定义见 [分类配置](../config/m2-data-taxonomy.json)。当前实际实现的材料/规则类别为：

| 分类维度 | 保存内容 | 扩充要求 |
| --- | --- | --- |
| 来源 | source_id、官网URL、文种、指纹、复核状态 | 官方原文、指南、解读分开；转载注明原始发布主体 |
| 地区 | 国家/省/市/区及受理范围 | 不把别区指南补成当前地区规则 |
| 事项 | 内部事项ID、申请原因和包含/排除范围 | 官方编码未知为未知；新增事项先核定范围 |
| 材料/规则类别 | 身份材料、户籍材料、适用条件、办理流程 | 对新类别补分类字典，避免只靠自由文本标签 |
| 适用条件 | 年龄、户籍地、申领原因、办理阶段 | 必交、条件交、择一、共享取得分别复核；初领/换领/补领分开 |
| 知识版本 | 固定version_id、来源清单指纹、日期、状态 | 新来源形成新快照，已有任务及交接仍读原版 |

现在的材料核验是两项模拟存在声明的预览清单，并把争议要求明确列为待复核；不是完整材料规则引擎。更多材料、条件分支、事项选择与正式发布规则需要在人工复核后扩展。

## 数据库扩大按这个顺序

| 顺序 | 要做什么 | 进入下一步的条件 |
| --- | --- | --- |
| 1 | 程千城核对当前事项、现行规则、材料差异和使用范围 | 有实际原文定位与复核人，未决规则有明确状态 |
| 2 | 正常取得省级规范及其他必要原件，补齐指纹、日期与来源登记 | 访问规则允许；没有个人申请记录；来源重复和转载已归组 |
| 3 | 先补齐一个事项的资料与材料分支 | 固定地区/事项/办理阶段，清单逐条连接原文，旧版可追溯 |
| 4 | 建立经人工核对的开发问题和独立验收任务 | 公开草案不冒充留出集，案例改写不跨组，指标有分母 |
| 5 | 扩展同事项的更多申请分支，再增加一个事项 | 两端页面与真实工具链再次验证，原/M1回归及空库边界通过 |
| 6 | 根据已积累资料评估全文索引、中文分词或向量检索 | 用实际检索任务比较效果、引用支持性、资源和失败率，再确定技术方案 |

不先追求条数。重复网页、同条款不同转载、同题改写均归同一来源或任务组；未确认、失效、冲突、使用依据不清和包含个人材料的数据进入待复核/拒收队列，不能混进已发布快照。

当前9条候选记录和30条问题草案继续用于资料复核准备。扩大数据库的责任仍是程千城负责官方资料与人工标准、负责人负责分类/导入/版本、陈子炫负责页面及独立验收。后续完成情况应由新的实际证据确认。
