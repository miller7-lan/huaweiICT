# 跨文档流程 V3：本机测试指南

日期：2026-11-14。对应分支 `claude/cross-document-process-optimization-71x1w4`。本文从拉代码写到上传结果，照着做即可；它取代原“本机测试与上传清单”。

云端这边看不到本机的 `.runtime` 私有记录，只能根据你上传到 GitHub 的内容判断下一步改哪里，所以第八节“上传什么”和前面的步骤同样重要。

## 一、总览

| 步骤 | 做什么 | 调用模型 | 大约耗时 |
| --- | --- | --- | --- |
| 1 | 拉代码、装依赖 | 否 | 5 分钟 |
| 2 | 准备 591 单元语料 | 否 | 1 分钟 |
| 3 | 定向测试 | 否 | 1 分钟 |
| 4 | 从已有记录导出诊断 | 否 | 1 分钟 |
| 5 | 只看检索证据 | 否 | 每题几秒 |
| 6 | 单题真实运行 | 是，每题最多 3 次 | 每题 10—30 秒 |
| 7 | 8 题配对对比并导出诊断 | 是，上限 32 次 | 几分钟 |

第 6、7 步消耗 DeepSeek 额度，执行前须取得用户确认。**如果时间只够做一件事，做第 4 步**：它不花额度，而且最能说明下一步该改哪里。

所有命令在仓库根目录、PowerShell 中执行。

## 二、步骤 1：拉代码、装依赖

```powershell
git fetch origin
git switch claude/cross-document-process-optimization-71x1w4
git pull
git log --oneline -1          # 记下提交号，写进执行报告

$env:PYTHONUTF8 = "1"         # 每开一个新终端都要设
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
.\.venv\Scripts\python.exe -c "import mcp, pydantic, sys; print(sys.version.split()[0], pydantic.VERSION)"
```

- 需要 Python 3.11 及以上。
- 不设 `PYTHONUTF8`，Windows 会按 GBK 读 UTF-8 文件而失败（上次执行报告里出现过）。
- `mcp` 必须是 `requirements.lock` 里的 1.26.0。装成 2.x 时，测试会在收集阶段报 `No module named 'mcp.server.fastmcp'`。
- 旧虚拟环境损坏时新建一个隔离环境再装，不要改业务代码去适应环境。

## 三、步骤 2：准备语料

V3 的“后端补来源标题”需要带标题和日期元数据的 591 单元语料。旧的 `.runtime/frozen-qa-20261030/corpus.json` 是 581 单元，没有标题单元。

上次验证时生成的 591 单元语料若还在，直接用它。否则从本机已有原件离线生成到一个新目录（不联网，不覆盖旧语料）：

```powershell
.\.venv\Scripts\python.exe scripts/build_frozen_corpus.py --offline --output-runtime .runtime/frozen-qa-v3-20261114
```

输出里 `unit_count` 应为 591。下文用 `<语料目录>` 指这个目录，用 `<语料目录>/corpus.json` 指语料文件。记下语料文件的散列，写进执行报告：

```powershell
(Get-FileHash <语料目录>/corpus.json -Algorithm SHA256).Hash
```

## 五、步骤 4：从已有记录导出诊断（不调用模型，最优先）

上次 8 题配对的私有记录还在本机，直接导出，不需要重跑：

```powershell
.\.venv\Scripts\python.exe scripts/export_flow_v3_diagnostics.py `
  --records .runtime/crossdoc-flow-v3/regression8-20261114/records.jsonl `
  --corpus <当时使用的 591 单元 corpus.json> `
  --output evidence/crossdoc-flow-v3/regression8-20261114-diagnostics.json
```

脚本按记录里的检索结果从语料重建证据，对最后一份模型草稿的每条结论单独重新核验。输出只有题号、结果类型、调用次数、失败码类型，以及每条结论的引用状态、字数和所引单元的类型，**不含任何题目、答案、结论、引文或证据文本**。

- `--corpus` 必须是当时运行用的那份语料，否则证据对不上。
- 输出必须是 `evidence/` 下的新文件，已存在会被拒绝（`NEW_FILE_UNDER_EVIDENCE_REQUIRED`）。
- 默认去掉失败码里的数值。加 `--with-values` 会保留（如 `QUANTITY_NOT_QUOTED:20元`）；这些数值来自模型草稿，上传前先自己看一遍。
- 这批记录由旧版 V3 生成，没有 `final_checks`、`claims_excerpted`，导出里对应为空，属正常。

终端打印的 `totals` 里重点看四个数：

| 字段 | 含义 |
| --- | --- |
| `claim_citation:valid / not_retrieved / quote_not_in_source` | 草稿里各条结论的引用状态 |
| `claim_fails_alone` | 单独核验不通过的结论数 |
| `claim_fixed_by_source_citations` | 其中补上来源标题或日期引用后就能通过的条数 |
| `draft_failure:<类型>` | 各类失败码出现的次数 |

## 六、步骤 5：只看检索证据（不调用模型）

```powershell
.\.venv\Scripts\python.exe scripts/run_frozen_qa.py ask --runtime <语料目录> "只读归档：……你的问题……"
```

输出是范围门的结果（`gate`）和检索到的证据（来源、定位、分数、前 200 字）。V3 的首轮检索与这里显示的相同。跨文档题先在这里确认两份资料都检索到了；没检索到的题，后面怎么改流程都答不出来。

## 七、步骤 6、7：真实运行

### 凭据与网络

- 密钥从环境变量 `DEEPSEEK_API_KEY` 读取，没有时读 `.runtime/deepseek/credentials.json`。两者都没有时，记录里的 `model.error` 为 `WAITING_DEEPSEEK_CREDENTIAL`。
- 沿用本机已配置的环境变量或系统代理，保留证书校验，不在命令或代码里写代理地址。
- 密钥不要出现在命令行历史、截图或执行报告里。

### 步骤 6：单题运行

```powershell
.\.venv\Scripts\python.exe scripts/run_frozen_qa.py ask --flow --live --max-calls 3 --runtime <语料目录> "只读归档：……"
```

各取一题：曾因年份或引用失败的、曾因证据不足停止的、应当停止的。终端输出里看：

| 字段 | 取值与含义 |
| --- | --- |
| `result_kind` | `answer` 完整答复；`answer_with_gaps` 通过核验但自述仍有缺项；`partial_answer` 部分答复；`stop` 停止 |
| `stop_origin` | `SCOPE_GATE` 范围门；`INSUFFICIENT_EVIDENCE_AFTER_FOLLOW_UP` 补查后仍不足；`MODEL_STOP_WITHOUT_MISSING_ITEMS` 模型停止且没说缺什么；`VERIFICATION_FAILED_AFTER_REPAIR` 修复后仍无可核验结论；`MODEL_OR_TOOL_ERROR` 调用或契约失败 |
| `checks` | 最后一份草稿的核验结果，不是最终展示内容的 |
| `answer` | 含“原文摘录：”的条目是转述没过核验、改为直接摘录的原文 |

完整记录在 `<语料目录>/runs/` 下，其中 `final_checks` 是对展示内容的重新核验，`model.calls` 是每次调用的结果和失败码，`retrieval.rounds` 是各轮检索新增的条数。

### 步骤 7：8 题配对对比

题目文件只含 `id`、`question`、可选 `context`，是一个列表，或 `{"cases": [...]}`；带参考答案的文件会被拒绝。仓库里的 `evaluation/crossdoc-refactor-20261113/fresh-questions.json`（V01—V06）可以直接当格式样例。

```powershell
# 先看计划，不调用模型
.\.venv\Scripts\python.exe scripts/compare_frozen_flow_v3.py --questions <8题文件> `
  --corpus <语料目录>/corpus.json --output .runtime/crossdoc-flow-v3/regression8-r2-20261114

# 确认 model_calls_at_most 后真实运行
.\.venv\Scripts\python.exe scripts/compare_frozen_flow_v3.py --questions <8题文件> `
  --corpus <语料目录>/corpus.json --output .runtime/crossdoc-flow-v3/regression8-r2-20261114 `
  --live --max-calls 32

# 导出这次运行的诊断
.\.venv\Scripts\python.exe scripts/export_flow_v3_diagnostics.py `
  --records .runtime/crossdoc-flow-v3/regression8-r2-20261114/records.jsonl `
  --corpus <语料目录>/corpus.json `
  --output evidence/crossdoc-flow-v3/regression8-r2-20261114-diagnostics.json
```

- 每题最多 4 次调用（单次流程 1 次，V3 最多 3 次），不重试；`--max-calls` 低于“题数 × 4”会被拒绝。
- 输出目录必须在 `.runtime` 下且不存在，旧记录不会被覆盖。
- 两种方法的先后顺序按 `--seed` 逐题打乱，默认 `20261114`。
- 答复通过核验后默认不再补查，所以 V3 实际调用通常少于上限。要复现 r2 当时的行为，加 `--follow-up-after-answer`。

这一轮只用来确认修正生效，看五项：

1. `summary.json` 里没有 `final_not_verified`；
2. 展示结论里的文号完整，如 `财综[2007]34号`；
3. 上次标 answer 却缺核心期限的 N02，这次是 `answer_with_gaps`；
4. 私有参考答案里标为“应停止”的题仍然停止。**这类题出现答复或部分答复就先停下，把题号告诉我，不继续后面的步骤**。以参考答案为准，不要按上一轮的实际结果推断哪些题该停（更正见下）；
5. 部分答复里出现了“原文摘录”条目，且摘录是完整的句子。

> **更正（2026-11-14）**：本文最初把这一条写成“应停止的 N05—N08”。这是我的错误：我把第一轮“N05—N08 都停止了”的实际结果当成了预期。按 Jev 三组对比的记录，N05、N06 是范围门停止，N07 是合理停止，而 N08 当时三组都按作答评分、失败原因是年份与引文绑定，应属应答复题。r2 报告据此条在 N08 处停下，属于按错误的检查项停止，不是流程放行了不该答的题。N08 的预期请以私有参考答案为准再确认一次。

同一批题重复运行会有生成波动，单次的增减不解读为提升或退步。这 8 题已用于开发，结果不能写成准确率。

## 十、常见问题

| 现象 | 原因与处理 |
| --- | --- |
| `UnicodeDecodeError: 'gbk' codec…` | 没设 `$env:PYTHONUTF8 = "1"` |
| `No module named 'mcp.server.fastmcp'` | `mcp` 装成了 2.x，按 `requirements.lock` 重装 |
| `Corpus missing: run scripts/build_frozen_corpus.py first` | `--runtime` 指向的目录里没有 `corpus.json`，回到步骤 2 |
| `OUTPUT_EXISTS_KEEP_ORIGINAL` | 输出目录已存在，换一个新运行名 |
| `PRIVATE_RUNTIME_OUTPUT_REQUIRED` | 对比脚本的 `--output` 不在 `.runtime` 下 |
| `--max-calls … is below the ceiling` | 上限小于“题数 × 4” |
| `NEW_FILE_UNDER_EVIDENCE_REQUIRED` | 导出文件不在 `evidence/` 下，或文件已存在 |
| `stop_reason` 为 `MODEL_ERROR` | 看记录的 `model.error`：`WAITING_DEEPSEEK_CREDENTIAL` 是缺密钥，`MODEL_CALL_BUDGET_EXHAUSTED` 是 `--max-calls` 用完；其余多为网络或输出格式问题。它不算答错，如实记入报告，不为此重跑整批 |
| 导出里结论的引用全是 `not_retrieved` | `--corpus` 不是当时运行用的那份语料 |

## 十一、我会怎么用上传的数据

| 导出里看到的情况 | 说明什么 | 下一步 |
| --- | --- | --- |
| 失败结论的引用状态多为“来源未检索”或“引文不在原文” | 模型抄写出错 | 做指针式引用（深化方案 A） |
| 引用有效，且 `claim_fixed_by_source_citations` 占多数 | 只差文件标题或日期引用 | 后端补引已够，重点转向完整性 |
| 引用有效，失败集中在金额、期限 | 需要人工看是真错还是规则误拦 | 真错：摘录降级已覆盖；误拦：改核验规则 |
| 停止题里补查新增为 0 | 语料里检索不到缺项 | 检索召回问题，做语料打标（深化方案 B 第 2 步） |
| 部分答复被判“漏核心”占多数 | 逐条保留不足以构成可接受答复 | 优先做证据矩阵（深化方案 B） |
| 应停止题出现答复或部分答复 | 放行了不该答的题 | 先停下排查，优先于其他一切 |

设计依据见[深化方案与参考文献](深化方案与参考文献-2026-11-14.md)，流程说明见[流程 V3 说明与测试方法](流程V3说明与测试方法-2026-11-14.md)。
