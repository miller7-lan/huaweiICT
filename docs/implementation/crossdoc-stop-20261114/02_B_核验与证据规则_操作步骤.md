## B3. 先实现结构和证据校验

按顺序检查：

1. Draft 的 task_id 与证据快照一致。
2. corpus_sha256、来源、定位和文本散列一致。
3. 每个 claim_id 唯一，每条结论列出的 evidence_ids 存在于本任务快照。
4. 引文非空，并能回到指定来源/位置中的连续原文。
5. 引文规范化规则显式记录；不进行模糊匹配后冒充原文逐字引用。
6. 派生表头等检索上下文不能作为原始引文。
7. 来源当前被阻断、版本不匹配或无法定位，返回明确问题，不能建议直接放开全库。

issues 必须关联具体 claim_id 和 evidence_id。给 A 的修复信息指向原证据或具体缺口，不替 A 编造新来源。

## B4. 实现停止合理性检查

不能把 stop_reason 非空当成停止合理。至少区分：

| 草稿表现 | 你的建议 |
| --- | --- |
| 泛称“证据不足”，没有具体缺口 | REPAIR_REQUIRED，要求说明缺哪个必需结论的依据 |
| 有明确缺口，尚可在范围内补查 | RETRIEVE_MORE，列出缺口和定向检索问题 |
| 现有证据可支持部分事实，尚未完成组合 | REPAIR_REQUIRED，列出已有支持和待组合项 |
| 确实缺少用户适用条件 | CLARIFY，不建议凭模型补造条件 |
| 已补查仍无关键依据，或存在未解决矛盾 | 建议 STOP，保留具体缺口或冲突 |
| 只看到关键词相关，无法证明足够或不足 | 保留 unknown，允许 A 按预算补查或修复，不能强制回答 |
| 外部模型或核验调用失败 | error/未完成，不能返回“不支持”的语义判断 |

范围、权限、来源和预算是否允许下一动作，最终由 A 决定。你可以返回理由，不自行改后端控制。

停止复核不要求自动证明任意复杂问题的全部证据充足性。第一轮只对已定义的必需事实项、来源和具体缺口作有界判断；无法判定就保留未知。

## B5. 实现逐条事实绑定

每条 Claim 除文本与证据 ID 外，按需要携带候选字段：

| 字段 | 示例与要求 |
| --- | --- |
| 对象/事项 | 首次申领、到期换领、遗失补领、损坏换领等必须分开 |
| 属性 | 费用、办理时限、证件有效期不能混为同一属性 |
| 数值原文 | 保留原文表示；数字规范化必须有显式规则 |
| 单位 | 元、日、工作日、自然日；原文未写日类型则保持未知 |
| 条件与例外 | 户籍、年龄、地区、时间、本人办理、特殊通道等 |
| 证据关系 | 支持哪一项，在哪个原文片段；不是任一引文出现过数字即可 |

模型填出的字段仍是候选，不能直接当真值。需要与原文中的实体、属性、数值和限定条件对应。

同一引文包含多个数字时，应检查它们分别属于什么属性。仅把全文数字集合改成“单引文数字集合”，仍无法拒绝“20元/60个工作日互换”。

由 A 在核验结束后生成引用序号。你只核验业务事实字段；不要通过“忽略所有数字”或删除事实数字来规避误拦截。

## B6. 加入针对性非数字核验

至少准备并覆盖：

- 必须本人办理 ↔ 可以代办；
- 仅适用于某一分支 ↔ 对所有分支适用；
- 普通办理时限 ↔ 特殊通道时限；
- 历史归档描述 ↔ 当前有效政策；
- 有条件允许 ↔ 无条件允许。

你负责定义 supported、contradicted、unknown、not_checked、error 的语义和各自处理，不要仅返回一个不可解释的分数。

可先对本场景采用明确的领域规则和人工校准样例；更复杂的语义判断通过 A 的显式适配器处理。它必须看到结论与原始证据，不能仅看其他 Agent 的摘要。

如果实例要求某项语义检查才能通过，而检查尚未执行或服务不可用，不能把它设为 supported。若使用仅有界规则的配置，输出要声明检查范围，C 不得把它报告为完整语义准确率。

## B7. 受控推导与修复建议

允许计算时，登记 rule_id、输入值、证据来源、输入单位、适用条件和输出单位，由程序计算与核对。

- 推导结果不必原样出现在原文，但必须有可复核的推导链。
- 不接受模型提供的任意 Python、表达式执行或未登记公式。
- 工作日与自然日不直接换算。
- 从条件规则推导结论时保留条件和例外。
- 源码、原文或版本不一致时不继续沿用缓存的结论。

对于错误草稿，返回“哪条结论、什么错误、需要修复或补查什么”，不要帮其拼凑无关引文通过检查。

## 三人必须使用的同一套接口约定

以下是**建议新增的 V2 约定**，不是声称仓库已有这些文件或 API。若同学的新实现已有等价结构，先复用并形成对应表。

由 B 先提交 `docs/implementation/crossdoc-v2-contract.md`，A 和 C 确认字段与示例，再冻结为 `crossdoc-v2-contract-1`。共用结构放在 B 负责的 `src/gov_mcp/frozen_qa_contracts_v2.py`，不要三人各写一份。

| 对象 | 至少包含 |
| --- | --- |
| EvidenceSnapshotV2 | task_id、corpus_sha256、按 evidence_id 查找的累计证据；每条含 source_id、locator、原文与 text_sha256 |
| DraftV2 | task_id、action、claims、missing_items、next_queries、reason_code |
| ClaimV2 | claim_id、结论原文、evidence_ids；需要时包含候选事实字段、引文片段和推导信息 |
| CheckResultV2 | recommendation、issues、missing_items、next_queries、claim_results、verification_status |
| TaskResultV2 | 服务端 decision、轮次和预算、最终对象或待处理事项、渲染文本、检查范围和版本 |

- `action` 为 `answer/retrieve_more/clarify/stop`。
- `recommendation` 是 B 的核验建议；**A 的后端结合权限、来源控制和剩余预算决定最终动作**。
- 后端决策采用 `VERIFIED/RETRIEVE_MORE/REPAIR_REQUIRED/CLARIFY/STOP/EXECUTION_FAILED`。其中 `CLARIFY` 明确表示需要用户补充适用条件，不冒充证据不足或已作答。
- `issues` 每项明确关联 claim_id、evidence_id（适用时）、错误码和具体原因。
- `verification_status` 区分已完成的检查、未覆盖的检查、unknown 和服务错误；不能把“只通过引用和数字检查”称作全部语义正确。
- `VERIFIED` 仅表示通过本实例已声明的必需检查，不等于现行政策有效、正式业务批准或完整语义真值。
- `RETRIEVE_MORE/REPAIR_REQUIRED` 不产生可交付的业务答案；`CLARIFY` 只产生澄清问题；`STOP` 只交付停止说明；`EXECUTION_FAILED` 只交付运行未完成说明。
- 原问题、语料版本和当前来源控制由 A 固定。模型自称“范围允许”或“检查通过”不能覆盖后端判断。
- **额外修复最多一轮**：可以包含一次定向补查、一次草稿修订、一次重核验；不一定每轮都需要补查。刷新、重试、并发请求和重启不能重置这一预算。
- B 的 `check_draft_v2(draft, snapshot, policy)`、`assess_stop_v2(draft, snapshot, policy)` 不直接调用模型或网络、不改任务状态；外部语义评估由 A 的显式适配器提供并标记来源。
- 最终答案从已核验结论渲染；如新增事实，必须重新核验，不能在最后自由增加内容。

**旧路径保留策略：**优先新增 V2 模块和脚本，保留旧 `frozen_qa.ask()/verify()`、旧 `METHODS` 和旧 A/B 结果。不得为了插入第三种方法而破坏原两方法盲评配对逻辑。

| G3 原生验收 | 运行新草稿并保留真实轨迹 | 查看真实核验输入与输出 | 比较 CLI/原生、新旧草稿和预算 | 实际运行能完成目标流程 |
| G4 新题评测与交付 | 固定版本并执行计划内运行 | 固定核验规则，处理独立复核意见 | 冻结题目、评分和报告，记录限制 | 结果可追溯，旧结果未改动 |

A/B/C 使用不同分支和模块，不在同一共享工作目录同时切换 Git 分支。若共用机器，使用独立工作目录或 worktree。分支操作前先检查已有改动，不强制清理。
