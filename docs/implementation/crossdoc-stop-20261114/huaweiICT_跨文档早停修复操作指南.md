# huaweiICT 跨文档早停修复操作指南

- 编写日期：2026-11-14（北京时间）
- 代码复核基线：`b5b58eb34b38cc4ba9a339f2e7111b6d9eb2cbb5`
- 适用问题：简单问答基本可用，跨文档问题经常提前停止，部分答案在引用或数字核验后被停止。
- 文档状态：**待实施的修改方案。本文不代表代码已经修改，也不代表改进后已经取得准确率成绩。**
- 本轮目标：保留现有角色与业务边界，先修复误停止、补查和引用修复闭环，再完善关键事实对应核验。

## 1. 先统一这次到底要改什么

本轮按以下顺序推进：

1. 查清一次停止发生在哪一层，补齐停止原因记录。
2. 将“模型认为证据不足”变成可补查的中间状态，允许一次定向补查。
3. 将可修复的引用、数字错误返回给生成环节，允许一次定向修复。
4. 让核验使用本次任务的累计证据，而不是重新只看原问题前 5 条。
5. 对本场景的对象、事项、数值、单位、条件和否定含义做针对性核验。
6. 通过开发用例和原生运行验收，再用新冻结题评价改进效果。

**第一轮暂缓：**重建整套知识图谱、再加两个通用盲审 Agent、全面接入额外付费核验、整批重建知识库。表格上下文只有在失败案例确实涉及表头或合并单元格丢失时提前处理。

不要把“提高成功率”理解为减少所有停止。隐私、权限、范围、来源控制、版本和证据不足仍应得到正确处理。

## 2. 已确认的事实与仍需确认的内容

| --- | --- | --- |

| 同学正在测试的实例 | 图片说明存在主、子 Agent 和新增 Jev 尝试 | 不能从图片确认其配置与仓库导出配置完全一致 |

代码复核中，用虚构输入观察到：

- 原文“20 元、60 个工作日”，答案改成“60 元、20 个工作日”，当前数字与引文检查仍可通过。
- 原文“必须本人办理，不得代办”，答案改成“可以委托他人代办”，当前检查仍可通过。

以上是核验函数的离线机制检查，**不是同学 16 次测试的重跑结果**。资料在知识库中、被检索返回、完整进入模型输入、足以支持结论，必须分别核对。

git branch --show-current

如果是仓库自由问答链，按本文后续文件落实；如果是另一套新配置，把相同处理规则落实到实际使用的编排代码。

**本步骤完成标准：**能够画清“问题 → 检索 → 生成 → 核验 → 最终答复”的真实调用顺序，并明确每一步由谁执行。

## 4. 步骤二：给所有停止分层记录原因

### 4.1 优先检查已有记录，避免重复消耗额度

仓库字面问答的记录位置：

- 单题：`.runtime/frozen-qa-20261030/runs/`
- 配对运行：`.runtime/frozen-qa-20261030/eval/<run_id>/records.jsonl`
- 原生运行：运行脚本记录的 SSE 日志与运行摘要。

若实际实例使用不同路径，以实例配置为准。

当前字面问答可以不调用模型，只查看检索：

```powershell
.\.venv\Scripts\python.exe scripts/run_frozen_qa.py ask "首次申领与到期换领的归档收费规定分别是什么？"
```

这条命令没有 `--live`，但要求本地已有冻结语料。其终端输出会截取证据文本，不能代替检查模型实际收到的完整上下文。

### 4.2 先按已有字段分类

| 已有记录特征 | 初步归类 | 下一步 |
| --- | --- | --- |
| `gate` 非空 | 范围或输入限制 | 核对是否正确触发，不统一放开 |
| `model_output.outcome=stop`，且核验通过 | 模型主动判断不足 | 查看其依据、缺口和实际输入 |
| 模型原本回答，`checks.failures` 非空，最终 `VERIFICATION_FAILED` | 核验后停止 | 对照具体错误码逐条检查 |
| `model.error` 或工具异常 | 调用或输出契约问题 | 保留原始错误类别，不能记成缺证据 |
| 原生轨迹显示步骤耗尽、超时或输出截断 | 执行预算问题 | 核对实际调用次数、长度和耗时 |
| 新增核验服务额度不足或不可用 | 外部核验未完成 | 保留任务，不伪装为证据不支持 |

注意：供应商返回 `finish_reason=stop` 通常只是本次生成正常结束，不能单凭这个字段判断业务误停止；它与模型输出里的 `outcome=stop` 不同。

### 4.3 新增日志字段

以下是**建议新增字段**，不是声称仓库已经支持：

```json
{
  "workflow_version": "crossdoc-v2",
  "task_id": "由服务端生成",
  "stop_origin": "MODEL_INSUFFICIENT_EVIDENCE",
  "stop_reason_code": "MISSING_REQUIRED_FACT",
  "missing_items": ["尚未找到适用于换领分支的费用依据"],
  "evidence_ids": ["E1", "E2"],
  "repair_rounds_used": 0,
  "model_calls": 1,
  "termination_reason": null
}
```

`stop_origin` 至少区分：范围限制、模型判断不足、引用错误、数字或单位错误、执行预算、模型或工具失败、外部核验不可用。

只在私有运行目录保存完整输入输出；可公开的摘要只保留必要计数、错误类别和脱敏信息。

**本步骤完成标准：**每次失败都能解释“在哪一层、因为什么结束”，不再只记录一个成功或失败标记。

## 5. 步骤三：修改“证据不足就直接结束”的逻辑

### 5.1 不再把任意非空停止理由视为合理停止

目前 `frozen_qa.py::verify()` 的停止分支没有充分判断停止是否合理。V2 应将以下问题分开：

1. 输出格式是否合格；
2. 已作答的结论是否通过核验；
3. 模型提出停止的理由是否应直接结束任务。

不要只将 `stop_reason` 写得更长，就视为通过停止复核。

### 5.2 增加草稿决策结构

建议保留旧 `AnswerOutput` 作为最终输出契约；在 V2 流程增加独立的草稿决策结构，例如：

- `action`：`answer`、`retrieve_more`、`clarify`、`stop`；
- `assertions`：已能提出的逐条结论；
- `missing_items`：缺少哪些支持结论的事实；
- `next_queries`：针对缺口的检索问题；
- `reason_code`：请求下一步处理的原因。

模型声明“硬停止”不能自行绕过后端判断；隐私、权限、来源和范围由后端现有控制规则决定。

### 5.3 根据缺口决定下一步

| 情况 | V2 动作 |
| --- | --- |
| 在允许范围内，但未查到某个关键依据 | 返回“需要补证据”，定向补查一次 |
| 已取得不同文档的证据，但尚未组合 | 返回原始证据及未完成的结论项，要求完成组合和核验 |
| 缺少必须由用户提供的适用条件 | 请求澄清，或说明条件分支；不能编造条件 |
| 关键依据实际不存在，补查后仍缺失 | 停止并明确缺口 |
| 隐私、权限、范围或来源控制阻断 | 按既有规则停止，不进入普通补查 |
| 模型、工具或核验服务调用失败 | 标记执行或核验未完成，不能当成事实不支持 |

**不得规定“只要有检索命中就必须回答”，也不得规定所有问题必须引用两份以上文档。** 证据是否足够取决于问题所需的关键结论。

### 5.4 先实现最小修复预算

第一版将额外修复限制为一轮：

- 原有流程先检索、生成、核验；
- 必要时额外补查最多一次；
- 对草稿定向修改最多一次；
- 修改后重新核验最多一次；
- 不足或不通过则按原因停止。

一次修复轮可以包含“补查 → 修改草稿 → 重核验”。所有额外调用由后端计数，刷新页面、重新调用工具或重启任务不能悄悄重置预算。

**本步骤完成标准：**模型首次提出证据不足时，不会在缺口尚可补查的情况下直接结束；真正缺证据时仍能停止。

## 6. 步骤四：让检索与核验共享累计证据

### 6.1 修改服务端的证据来源

重点修改 `frozen_qa_server.py::FrozenQAService.retrieve()` 和 `verify()` 对应的 V2 路径。

当前字面问答核验会重新调用原问题检索。如果只修改检索而不修改核验证据来源，补查取得的证据可能被判为 `CITATION_NOT_RETRIEVED`。

V2 每个任务保存以下内容：

| 字段 | 要求 |
| --- | --- |
| `task_id` | 服务端生成并校验任务归属 |
| 原问题与适用范围 | 固定在任务中，不能用改写后的问题绕过检查 |
| `corpus_sha256` | 固定本次使用的语料版本 |
| 查询轮次、缺口、子查询 | 能回溯为什么补查 |
| 累计证据表 | 合并原检索与补检索结果，去重保存 |
| 草稿版本与核验结果 | 明确一次修复对应哪份草稿 |
| 预算计数 | 由后端控制，不由模型自行声明 |

证据 ID 由服务端分配，绑定至少：`source_id`、`locator`、原文、文本散列和语料版本。ID 不应在每轮检索中按排名重新编号，否则 E1 可能在不同轮代表不同原文。

### 6.2 字面检索与原生知识库分别接入

- **字面检索入口：**按子问题分别查询，合并到任务证据表。
- **原生知识库入口：**保留现有知识库检索；将结果的来源、定位映射回冻结语料，再加入任务证据表。来源 ID 的推导与校验尽量交给程序，不让模型仅凭文件名自行拼写。
- 新任务使用独立证据集合，不能因为另一任务查到过某条证据，就自动视为本任务已取得。

本轮优先打通同学实际使用的那个入口，不必同时上线两套入口。

### 6.3 第一版检索策略

先把跨文档问题拆成需要回答的事实项，每项单独检索。每项前 5 条可以作为开发初值，合并去重后检查覆盖；不要仅把全局 `TOP_K` 调大就认为完成修复。

检查模型实际输入是否包含：

- 支持每个必答结论的原文；
- 对象、分支、条件与例外；
- 相邻段落或必要表格上下文；
- 未被工具观察压缩、截断的关键内容。

**本步骤完成标准：**补查得到的合法证据能参与核验，跨任务、跨版本或无法定位的引用仍被拒绝。

## 7. 步骤五：引用错误先修复，事实错误仍拦截

### 7.1 核验返回具体问题，而不是立即抹掉全部草稿

建议 V2 返回如下结构；字段及状态需要实现后才可使用：

```json
{
  "decision": "REPAIR_REQUIRED",
  "issues": [
    {
      "claim_id": "C2",
      "code": "QUOTE_NOT_IN_SOURCE",
      "evidence_id": "E4",
      "message": "该引文不是E4中的连续原文"
    }
  ],
  "remaining_repair_rounds": 1,
  "final": null
}
```

建议决策状态：

| 状态 | 含义 | 能否直接作为业务答案交付 |
| --- | --- | --- |
| `VERIFIED` | 草稿通过本轮要求的核验 | 可以，保留历史资料和未知项说明 |
| `RETRIEVE_MORE` | 有明确证据缺口且仍有预算 | 不可以，先补查 |
| `REPAIR_REQUIRED` | 有明确可修复问题且仍有预算 | 不可以，先修复 |
| `STOP` | 合理停止，说明范围或未解决缺口 | 可以交付停止说明 |
| `EXECUTION_FAILED` | 调用、输出契约、预算或外部服务失败 | 只能交付运行未完成说明 |

旧接口的 `passed` 不应被直接解释为“业务答案完整正确”。V2 用明确的 `decision` 控制流程，中间状态的 `final` 为空。

### 7.2 区分哪些错误可以修复

| 问题 | 可以怎么修 | 不允许的处理 |
| --- | --- | --- |
| 来源或定位抄写错 | 根据证据 ID 取回正确来源和位置 | 猜一个相似文档代替 |
| 引文拼接、标点或边界问题 | 从已取得的原文重新选择连续片段，再核验 | 模糊匹配后直接声称逐字引用 |
| 引用编号被当成事实数字 | 将引注与事实字段分开；由后端渲染引用编号 | 为规避检查删除所有数字 |
| 结论中的金额、期限没有依据 | 补证据，或修改、删除对应结论 | 添加无关引文凑出相同数字 |
| 对象、分支、单位或例外不匹配 | 纠正该结论并重核验 | 降低阈值强行通过 |
| 本次任务未取得引用证据 | 补查或注册合法检索结果后再核验 | 直接放开对全库任意引用 |
| 修复后仍不通过 | 停止并说明未解决问题 | 无限循环或跳过核验 |

最终答复应由已核验的结论和证据表渲染。若最后又让模型自由改写整份答复，新增事实也必须被重新核验。

**本步骤完成标准：**可修复的引用错误能进入一次修复，错误事实不会因放宽引用检查而通过。

## 8. 步骤六：补齐本场景的关键事实对应检查

先覆盖以下高频字段，不把“核验所有自然语言含义”作为第一轮完成条件：

1. 事项：首次申领、到期换领、遗失补领、损坏换领等。
2. 数值及指标：费用、办理时限、有效期限。
3. 单位：元、日、工作日、自然日；原文未注明日类型时保持未知。
4. 条件：户籍、年龄、办理方式、地区、时间或版本。
5. 否定与例外：本人办理、不得代办、仅限某类对象、特殊通道等。

### 8.1 每条结论绑定自己的证据

建议 V2 在现有 `Assertion` 思路上增加：

- `claim_id`；
- `evidence_ids`；
- 可核对的对象、事项、属性、数值、单位和条件；
- 如有推导，记录操作数来源和规则。

仅把“全文数字集合检查”改成“每条引文数字集合检查”仍不充分，因为同一段引文可能同时包含金额和时限。

### 8.2 将程序检查与语义检查分工

- 程序：来源、定位、散列、版本、引文连续性、字段类型、数字单位、已登记规则和执行预算。
- 模型或人工复核：结论是否被原文支持，否定、条件和例外是否遗漏。
- 语义判断必须看到实际原文及结论，不能只查看上一 Agent 的摘要。
- 有相关原文不等于其支持全部结论；无法判定的含义保留未核定状态。

### 8.3 推导数字单独处理

允许的计算应由登记的规则执行，记录输入值、来源、单位及结果。推导结果未原样出现在原文中，不应仅因此失败；但不能让模型任意生成代码并执行。

不同日期单位不能直接相减或换算，历史归档不能自动作为现行政策或实际应缴金额的依据。

**本步骤完成标准：**金额与时限互换、事项分支错用、否定含义反转等针对性错误能够被发现；不得把若干规则通过宣传为完整语义正确。

## 9. 步骤七：同步修改 Agent 配置和运行脚本

### 9.1 修改生成提示词的脚本

实际使用哪个入口，就优先修改对应脚本：

- `scripts/provision_frozen_qa_native.py`
- `scripts/provision_frozen_kb_native.py`

需要明确的新规则：

1. 保留范围、来源、隐私和权限要求。
2. 发现证据缺口时，按服务端决策进行一次补查。
3. 核验要求修复时，只修改指出的问题，再核验一次。
4. 不自行重置预算或重复已经成功完成且无需重做的步骤。
5. 工具出错按实际错误停止，不能编造成证据不足。
6. 只从经过核验的最终对象生成答复。

替换无条件的“Never repeat a tool call”，改成“只按服务端剩余预算及状态进行指定重试”。不能将允许一次补查理解为允许重复所有动作。

### 9.2 创建 V2 草稿，避免覆盖旧实例

基线脚本包含硬编码的名称和账本路径：

| 脚本 | 现有重要位置 |
| --- | --- |
| `provision_frozen_qa_native.py` | `RUNTIME`、`OUTPUT`、`NAME`、`DISPLAY`、`SERVICE/PORT`、`native-drafts.json` |
| `provision_frozen_kb_native.py` | `RUNTIME`、`LEDGER`、`OUTPUT`、`NAME`、`DISPLAY`、检索工具和核验工具绑定 |

在 V2 中新增或明确传入独立的草稿名称、部署账本、运行输出和服务绑定。确认新账本不含旧 Agent ID，读回关联关系后再调试。

**不要只改提示词然后直接对原账本运行 `--apply`。** 脚本可能按账本更新旧 Agent。仅复制导出 JSON，也不能保证下一次脚本生成时保留修改。

现有语料可只读复用；新服务与旧服务若同时运行，应使用独立名称和经检查未占用的端口。现有服务会检查启动时源码指纹，改代码后可能返回 `SERVICE_SOURCE_CHANGED_RESTART_REQUIRED`，需要按实例管理方式重启对应新服务，不能随意关闭他人正在使用的服务。

### 9.3 同步 CLI 与原生运行路径

这两条路径不同，不能只改一条就声称整体修复：

- CLI：`scripts/run_frozen_qa.py` → `frozen_qa.ask()`。
- 原生：Nexent Agent → MCP 服务 → `FrozenQAService`，并由 `scripts/run_frozen_qa_native.py` 记录运行。

建议在 V2 新入口中复用同一套状态转换、证据表和预算规则，保持判断一致。保留旧接口及旧基线的可复现路径。

**不要直接把第三种方法追加到现有 `METHODS` 并复用原 A/B 盲评脚本。** 原脚本按两种方法配对、打乱和标注。V2 应有独立入口或显式选择两种方法的新比较脚本，旧正式运行不变。

### 9.4 检查真实运行预算

基线原生草稿的 `max_steps=6`，运行脚本还有 `MAX_MODEL_STARTS=8`、时间和流量限制。新增补查后，必须检查：

- 主、子 Agent 的实际模型启动数；
- 工具调用数与单次输出长度；
- 输出是否被截断；
- 完整一轮的墙钟时间；
- 修复轮数、模型调用上限与原生步骤限制是否互相冲突。

工具调用数、模型 API 调用数、平台模型启动数不是同一个计数。根据实际轨迹设置 V2 的有界预算，不直接把所有上限翻倍。

**本步骤完成标准：**新草稿确实执行新的补查与修复流程；旧配置未被覆盖；CLI 与原生链的关键判断一致。

## 11. 验证顺序与验收用例

### 11.1 先做离线定向检查

使用虚构文本和明确的输出夹具，不调用云模型。当前仓库的定向测试命令：

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_frozen_qa.py -q
```

V2 测试文件实现后，再运行对应文件。Linux/macOS 可使用项目自己的虚拟环境 Python 执行相同 `-m pytest` 参数。

| 编号 | 用例 | 预期 |
| --- | --- | --- |
| T01 | 证据已齐，草稿仍泛称“证据不足” | 不因非空停止理由直接结束；进入停止复核 |
| T02 | 缺一项明确依据，仍有预算 | 返回补查需求；补查后累计证据可用 |
| T03 | 补查后关键证据仍不存在 | 正确停止，并列出未解决缺口 |
| T04 | 来源、定位或引文边界可修复 | 一次修复后重核验；不模糊放行 |
| T05 | 正确事实带后端引用编号 | 引注数字不作为业务事实误拦截 |
| T06 | “20元、60个工作日”写反 | 对应关系不通过 |
| T07 | 首次申领与换领规则混用 | 对象或事项分支不通过 |
| T08 | 工作日与自然日直接换算 | 不通过或保持未知 |
| T09 | “不得代办”改成“可以代办” | 语义检查发现反转 |
| T10 | 超范围或隐私输入 | 保持正确停止，不进入补查 |
| T11 | 新证据属于其他任务或其他语料版本 | 拒绝使用 |
| T12 | 修复轮次已用完 | 不再调用生成或检索，给出明确终态 |
| T13 | 模型或外部核验额度不足 | 记录运行未完成，不记为证据不支持 |
| T14 | 最后输出试图加入未核验事实 | 不交付新增事实，或重新核验 |
| T15 | CLI 与原生入口使用相同草稿和证据 | 核心决策一致 |

对 T09 等语义用例：离线夹具只能证明接口与分支正确；真实模型能否稳定识别，必须在后续模型实验中另测，不能用模拟返回证明语义准确率。

### 11.2 再做小规模原生调试

离线检查通过后，使用新草稿和开发问题验证：

1. 一道普通单文档问题，确认原本可用的能力没有退化。
2. 一道需要两份资料的跨文档问题。
3. 一道需要补查的问题。
4. 一道可修复引用错误的问题。
5. 一道应当停止的问题。

逐条保留实际工具顺序、模型启动数、核验问题、修复轮次和最终对象。根据实际预算安排，不因为“还没成功”就无上限追加调用。

只有在新实例、令牌、知识库和授权均已配置后才运行真实调试；本文不提供一个绕过现有配置直接执行的付费调用命令。

### 11.3 最后进行新题效果评测

- 旧 30 题正式成绩和旧运行原样保留。
- 开发失败案例可以用于定位与调试，但不能再宣称是新的独立测试。
- 对改进方案另出新题，冻结题目、参考、语料、模型配置和评分口径，再比较旧流程与 V2。
- 如需比较 Jev，另设清楚标记的对照，不与旧结果混合。
- 同一语料和模型用于对比；新增检索和修复产生的成本差异如实记录。

至少报告：

| 指标 | 说明 |
| --- | --- |
| 应答复题正确率 | 应该回答的问题是否给出可接受结论 |
| 误停止率 | 应答复题中实际停止的比例 |
| 正确停止率 | 应停止题中恰当停止的比例 |
| 引用与事实对应错误 | 分开记录定位错误和含义不支持 |
| 执行完成率 | 工具、格式、步骤、超时等问题 |
| 平均调用数与耗时 | 同时报告触发修复的比例 |
| token 或实际成本 | 可观测多少就报告多少，缺失写未知 |

不能只用“最终回答了多少题”评价改进。

## 12. Jev 与表格问题的后续处理

### 12.1 Jev

当前新增 Jev 的真实接线尚未核对。先保留其配置和试验，不把它作为本轮早停修复的必需前提。

- 用原问题、逐条结论和实际原文检验它能否识别不支持、矛盾或缺条件。
- 服务异常、额度不足、翻译失败与语义判断结果分开。
- 如果某部署将 Jev 设为必须通过的门，服务不可用时保持“未完成核验”，不能静默当成已通过。
- 可以在独立实例运行旧链对照，但必须说明两套链的核验配置不同。
- 仓库已有适配含翻译路径；是否沿用该路径须看同学新配置，不默认假设其调用次数和成本。
- 不为获得预期结果随意调整阈值；改动后用新样例复核。

### 12.2 表格上下文

若确认失败来自孤立行、缺表头或合并单元格信息，再修改 `build_frozen_corpus.py::xlsx_units()`：

1. 保存原始单元格与坐标。
2. 增加表头、父级项目和合并单元格所属关系作为检索上下文。
3. 派生上下文与原始引文分开存储，不能把补全内容冒充原文连续片段。
4. 在新语料版本中重建受影响单元与索引，保留旧语料散列及旧结果。
5. 先定向检查受影响表格，不立即重建全部 581 块。
