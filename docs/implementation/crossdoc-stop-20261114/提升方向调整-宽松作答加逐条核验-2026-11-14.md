# 提升方向调整：宽松作答 + 逐条核验

日期：2026-11-14。依据：[30 题盲评结果](../../competition/30题盲评结果-2026-11-07.md)、[r2 诊断分析](r2诊断分析与下一步-2026-11-14.md)、[人工判读结果与下一步规划](人工判读结果与下一步规划-2026-11-14.md)。

**状态：方向调整和配套代码已完成，均为离线验证（V3 相关测试 24 项通过），没有新的真实模型运行。这个方向是否成立，要靠本文第四节的回放数据来判断，现在还没有结论。**

## 一、选定的方向

把“谨慎”从提示词里拿出来，放到作答之后的程序检查里：

- **作答**：用接近基线的宽松提示词，让模型像基线那样把能答的都答出来。
- **把关**：范围门照旧在作答之前拦截；作答之后逐条核验，通过的保留，转述没通过但引文是原文的换成原文摘录，其余丢弃；没有一条通过就停止。

现在的 V3 是“严格提示词 + 逐条核验”。这次增加一个“宽松提示词”选项，其余流程完全相同，然后用已有数据比较两者，再决定哪个作为新题评测的被测版本。

## 二、为什么是这个方向

30 题正式盲评里，两种方法用的是同一套检索、同一个模型，差别只在提示词和核验：

| | 基线（宽松提示词，不核验） | 原方案（严格提示词，核验即停） |
| --- | --- | --- |
| 应答复题实际作答 | 18/20 | 11/20 |
| 应停止题实际停止 | 6/10 | 10/10 |
| 跨文档题可接受（评分次数） | 15/16 | 3/16 |

原方案 9 次误停止的构成：5 次是作答后核验失败，4 次是模型自己判断“证据不足”。

- 前 5 次，V3 的后处理（后端补来源引用、修复、逐条保留）就是为它们做的，r2 的 8 道开发题上已经看到效果。
- 后 4 次，后处理帮不上：模型根本没有作答。而同样的证据下，基线答了，而且评审认为可接受。差别来自严格提示词——它要求“证据不能直接支持就停止”，还带着一长串针对具体题目的规则。

所以剩下最大的一块提升空间，是让模型先答出来。风险也清楚：基线在应停止题上只停对 6 道。宽松提示词会不会把应停止题放出来，取决于范围门和逐条核验能接住多少。这正是需要数据回答的问题。

其他方向为什么排在后面：

| 方向 | 判断 |
| --- | --- |
| 证据矩阵 | 人工判读显示完整性问题不突出（10 次评分里漏核心 1 次），投入大，暂缓 |
| 指针式引用 | 71 条草稿结论的引用全部有效，没有要解决的问题 |
| 更多补查轮次 | 9 次补查没有一次改变结果类型 |
| Jev 逐条打分 | 没有足够的正反样本做校准 |
| 给缺标题的来源补元数据 | 值得做，但只影响涉及个别来源的题，是补漏而不是主要增量 |

## 三、代码改了什么

1. **`frozen_qa_flow_v3.ask` 增加 `rules` 参数**：`strict`（默认，现有行为）或 `light`。`light` 的系统提示词是基线的通用规则加四条短规则：归档不代表现行；每条结论的数字和单位要在它自己的引文里；能答的先答、缺的写入未知项；否定不得写成可以。**不含任何针对具体事项的规则。** 检索、范围门、核验、修复、逐条保留对两种提示词完全相同。
2. **对比脚本增加 `--flow-rules strict|light`**，写入计划和记录。
3. **导出脚本的离线回放支持 30 题正式评测的留存记录**：
   - 回放前先过范围门，包括对当时没有范围门的基线记录；
   - 新增 `--expected`，读取私有参考里每题“应答复 / 应停止”，输出“应有结果 × 当时结果 × 回放结果”的计数表；
   - 新增 `evidence_units_missing_in_corpus`，语料对不上时能看出来。

## 四、怎么验证

### 第 1 步：对 30 题正式评测的留存草稿做回放（不调用模型，先做）

30 题那次运行的 60 份模型草稿还在本机。回放把每份草稿交给现在的后处理，看不再调用模型时会展示什么：

```powershell
$env:PYTHONUTF8 = "1"
git fetch origin; git switch claude/cross-document-process-optimization-71x1w4; git pull

.\.venv\Scripts\python.exe scripts/export_flow_v3_diagnostics.py `
  --records .runtime/frozen-qa-20261030/eval/20261105T003300Z/records.jsonl `
  --corpus <591 单元 corpus.json> `
  --expected <私有 reference.json> `
  --output evidence/crossdoc-flow-v3/holdout30-20261105T003300Z-replay.json
```

- `--corpus` 用 591 单元那份（原 581 个内容单元都在里面，另有标题和日期单元供后端补引）。导出里 `evidence_units_missing_in_corpus` 应全为 0；不为 0 说明语料对不上，结果不可用。
- `--expected` 指向出题时冻结的 `reference.json`。脚本只读其中的题号和 `expected_outcome`，输出里只有计数。
- 这次运行的记录早于 V3，字段不全属正常。

终端会打印 `by_expected_outcome`，形如：

```
baseline: expected_answer {recorded:answer 18, recorded:stop 2, replayed:answer .., replayed:partial_answer .., replayed:stop ..}
          expected_stop   {recorded:answer 4,  recorded:stop 6, replayed:stop ..,  replayed:answer .., ...}
proposed: expected_answer {recorded:answer 11, recorded:stop 9, replayed:...}
          expected_stop   {recorded:stop 10, replayed:...}
```

其中两行回放结果对应两种候选：

| 回放的是 | 相当于 | 回答的问题 |
| --- | --- | --- |
| 原方案草稿 | 严格提示词 + 逐条核验（现在的 V3，不含修复和补查） | 5 次核验误停能救回几次；10/10 的停止是否保住 |
| 基线草稿 | 宽松提示词 + 范围门 + 逐条核验（本次调整的方向） | 18 份答复经过核验还剩多少；4 道本该停止却作答的题能拦下几道 |

回放不含“修复一次”，所以实际运行的答复数只会不低于回放值。

### 第 2 步：按回放结果决定

把应答复题的“答复 + 部分答复”数和应停止题的“停止”数放在一起看：

| 回放结果 | 决定 |
| --- | --- |
| 基线草稿这一行：应答复题保留数明显高于原方案草稿，且应停止题停止数不低于 9/10 | 采用 `light` 作为新题评测的被测版本 |
| 基线草稿这一行：应停止题停止数明显低于原方案草稿 | 宽松提示词放出了不该答的题，保持 `strict`；再看被放出的题属于哪一类（版本冲突、分支、证据不足），考虑能否加一道确定性检查 |
| 两行差不多 | 保持 `strict`，不增加变量 |
| 部分答复和摘录很多 | 先抽几份人工看摘录是否相关，再决定；这是摘录第一次在真实草稿上触发 |

“明显”没有统计意义上的阈值，30 题太少；差 1、2 题视为相同。

### 第 3 步：小规模真实运行（需确认额度）

回放用的基线草稿是用旧的“字面前 5 条”检索生成的，和现在的检索不同。回放支持 `light` 时，再用 8 道开发题真实跑一次确认：

```powershell
.\.venv\Scripts\python.exe scripts/compare_frozen_flow_v3.py --questions <8题文件> `
  --corpus <语料目录>/corpus.json --flow-rules light `
  --output .runtime/crossdoc-flow-v3/regression8-light-20261114 --live --max-calls 32
```

跑完照常导出诊断。看三项：应停止的题（以参考答案为准）是否仍停止；答复数是否不低于 r2 的 5 份；`claims_excerpted` 和 `claims_dropped` 是否增多。

### 第 4 步：新题正式评测

被测版本按前三步的结论冻结（提交号和 `--flow-rules` 取值都写进冻结记录），其余按[下一步规划](人工判读结果与下一步规划-2026-11-14.md)第三步执行。

## 五、这个方向的风险

- **宽松提示词可能增加程序查不出的错误。** 逐条核验只能确认引文是原文、数字和单位对得上，判断不了“把换领的规定套到补领”这类语义错位。基线在应答复题上有 10/40 次评分被判有事实错误，其中多少能被逐条核验拦下，回放之后才知道，而且要结合人工评分看。
- **回放是对已用过的题做事后分析。** 它只用来选方向，不是成绩，不能写成“在 30 题上提升到多少”。30 题的正式结论不变。
- **回放不等于真实运行。** 草稿是旧检索、旧提示词生成的；`light` 的提示词也不完全等同于基线。所以有第 3 步。
- **应停止题里靠模型自己判断停下来的那几道**（证据不足、版本冲突），在宽松提示词下最容易被放出来，是重点观察对象。

## 七、一句话

V3 已经解决“答了却被核验拦下”的那一半误停；另一半是“模型不敢答”，最可能的解法是换成宽松提示词，把把关交给程序。第 1 步不花额度就能看出这条路走不走得通，请先做第 1 步并上传结果。
