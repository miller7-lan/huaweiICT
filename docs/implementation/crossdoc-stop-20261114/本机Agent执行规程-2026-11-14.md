# 本机 Agent 执行规程（跨文档流程 V3）

读者：在本机执行 V3 相关测试、评测、原生运行、评审收表的 Agent。本轮的具体任务和逐项硬性要求见[第二份规程](本机Agent执行规程-第二份-本轮任务-2026-11-15.md)。命令在[本机待测清单](本机待测清单-2026-11-14.md)，本文只规定**怎样执行才不让结果打折**。两者冲突时以本文为准。

上一轮的结果被打了七处折扣：出题与执行在同一会话、原生服务用了另一套提示词、应停止题没有区分度、评分表不合规后被代为规范化、一列评分被误读、截图缺失、应停止题名单曾按运行结果推断。每一处都对应下面一条规则。

## 三个词

- **冻结**：一轮开始前写定、之后不变的东西：被测提交、提示词方案、被测方法、语料、题目、参考答案、判定口径。
- **阻断**：条件不满足，这一步不开始。写明缺什么，交回给用户，然后停下。
- **降级**：可以执行，但这一轮只能叫“开发对比”，并在报告开头逐条写出折扣。

## 开跑前：预检

任何会调用模型的步骤之前，先运行预检，由它给出这一轮的名称：

```powershell
.\.venv\Scripts\python.exe scripts/flow_v3_preflight.py --round <本轮声明.json> `
  --questions <题目> --reference <参考> --corpus <语料> [--native] `
  --output evidence/crossdoc-flow-v3/<本轮名>-preflight.json
```

本轮声明照 `evaluation/crossdoc-flow-v3/round-template.json` 填写。其中六项独立性条件是**事实声明，由用户提供**。用户没有明确说“是”的，一律填 `false`；向用户问清楚，问不到就保持 `false`。

| 预检结果 | 做什么 |
| --- | --- |
| `BLOCKED` | 阻断。把 `blocked` 列表原样交给用户，等用户处理后重新预检 |
| `development` | 降级。可以执行；报告标题、文件名、所有表述都用“开发对比”，开头逐条照抄 `discounts` |
| `formal` | 可以称“正式评测” |

完成标准：预检文件已生成，且它的 `label` 就是后续报告使用的名称。

## 每类工作的规则

### 出题

题目由**另一个环境**产生：它只拿到七份冻结资料原文和[出题说明](../../../evaluation/crossdoc-flow-v3/出题说明-给隔离出题环境.md)。执行评测的会话读过 V3 代码和诊断，因此由它出的题只能用于开发对比。

用户要求当前会话出题时：照做，并把声明里前两项独立性条件填 `false`。这一轮是开发对比。

参考答案里每题的“应答复 / 应停止”是唯一依据。运行结果、上一轮的停止情况、题面里的字眼，都用来核对，而由参考决定。

### 运行

- 一轮使用同一个冻结的提示词方案：命令行、三方法对比、原生服务全部一致。原生运行前带 `--native` 再预检一次。
- 每个运行只执行一次，输出目录用新名字。调用失败照实记录；失败的那一次也是结果的一部分。
- 运行中发现代码问题：记录下来，本轮继续用冻结的提交跑完，修改留到下一轮。
- 额度：每一步的调用上限写在清单里，开始前向用户确认。

完成标准：`plan.json` 里的提交、方案、语料散列、题目与参考散列与预检文件一致；`summary.json` 的 `model_calls` 不超过上限。

### 应停止题的区分度

三方法运行结束后，查看基线在应停止题上的停止数。**基线也全部停住时**，这批应停止题没有区分度，在报告的折扣里加一条“应停止题未能区分方法”，并且不用这一轮说明停止能力。

### 原生运行

每道原生题的完成标准，四条都要有：

1. `passed` 为 true，工具顺序以 `govkb_flow_open` 开头；
2. 最终答复与服务端任务文件的 `final` 一致；
3. `model_starts` 的数值已写进报告（达到 9 或 10 时单独标出）；
4. 调试界面截图两张已保存。

截图拿不到时，这一步的状态是“未完成：缺截图”，照这样写。

### 评审收表

- 评审包发给评审时不含 `key.json`。
- 每张表交回后立刻检查：

  ```powershell
  .\.venv\Scripts\python.exe scripts/score_flow_v3_review.py --pack <评审包> --sheets <这张表>.csv --check
  ```

  有问题时，把问题列表原样发还评审，由评审本人修改后重交。**评分值只由评审本人填写和修改。**
- 自制的表单（如可填写 PDF）：每个评分项的说明照抄 `review.md` 开头的规则表原文，导入脚本遇到不合规的行直接拒绝。
- 两张表都通过检查后才统计。统计结果里 `sheets_passed_rule_check_unchanged` 应为 true。

完成标准：两张表各自 `--check` 的 `problems` 为空，统计 JSON 已生成。

## 回报格式

每一轮结束写一份报告，开头固定这五行：

```
名称：<正式评测 | 开发对比>（取自预检文件）
被测提交 / 提示词方案 / 语料单元散列：
折扣：<逐条照抄预检的 discounts；运行后新增的折扣接在后面；没有就写“无”>
未完成：<每一项没达到完成标准的步骤及原因；没有就写“无”>
调用：<实际次数 / 上限，失败次数，重试次数>
```

正文里：

- 数字只写清单各步要求上传的计数，并注明来自哪个文件。
- 程序标签（有答复、带缺项、部分答复、停止）照原样写；“答对”“准确率”只在人工评分之后、引用评分统计时使用。
- 不同轮次的成绩分开列。
- 做了清单之外的事（多跑一题、换了参数、改了文件），单独列一节说明做了什么和为什么。

## 需要停下来问用户的情况

- 预检结果是 `BLOCKED`。
- 一步的结果会改变后面步骤的参数（例如某项对比的结论决定用哪个提示词方案）：报告结果，由用户确认后再继续。
- 清单没有覆盖的情况，或两份文档说法不一致。
- 应停止的题给出了答复。
