## 1. 取得与核验工程包

项目根目录运行以下命令，只使用 Python 标准库，不请求网络、模型或 Nexent，不读取 `.runtime`，不修改旧预算：

```powershell
.\.venv\Scripts\python.exe scripts\build_competition_package.py
.\.venv\Scripts\python.exe scripts\build_competition_package.py --verify-only
```

没有 `.venv` 时，也可用已有 Python 3.11+ 执行打包脚本。输出位于 `artifacts/competition-20261021/`：

| 文件 | 用途 |
| --- | --- |
| `ict-topic3-public-engineering-20261021.zip` | 按当前工作区白名单生成的工程包 |
| `manifest.json` | 每个工程文件的路径、字节数、SHA-256、范围和缺项；ZIP 内有相同副本 |
| `SHA256SUMS.txt` | 工程文件校验清单，ZIP 内有相同副本 |
| `PACKAGE-SHA256.txt` | ZIP 文件整体散列 |
| `source-requirements.json` | 南京2份、河南更新2份及多模态准备3份，共7份原件的官方URL、预期散列及取得要求 |
| `PACKAGE-NOTICE.md` | 交付边界与许可说明 |
| `verification.json` | ZIP 成员、文件散列、CRC、凭据与路径的定向核验结果 |

在发送方提供整体散列后，接收方先核对 ZIP 的 SHA-256，再解压到**新的目录**，运行包内的打包脚本重新生成并核验。脚本默认从自身上级目录取源，输出仅覆盖上述已知文件；不会清理原有工程目录。散列证明文件一致性，不能替代发送方身份或签名。

验证检查严格匹配成员清单，拒绝绝对路径、上级路径、重复成员、软链接、运行目录、数据库、日志、密钥文件和明文凭据特征。所有 JSON 的凭据字段必须为空；`credential_ref` 只允许 `env:变量名`。`config/decision/connections.json` 保留 `inference_enabled=false` 与 `form_verifier_enabled=false`。

## 3. 新机器的分层准备

参考环境为 Windows、Python 3.12、Git、Docker Desktop/WSL2；项目声明 Python 3.11+。Nexent 固定为 v2.7.0、提交 `519b9b17c7f4cbc623256ac318ea96a20f33772e`。Docker 镜像、官方 Nexent 源码、Python 依赖及模型分别从其合法来源取得，遵循各自许可，不从旧机器复制私有部署卷。

安装与部署命令**会访问网络或改变本机环境**，不由打包过程执行。接收方准备好网络与资源后，可从独立的新工程目录运行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\setup.ps1
.\.venv\Scripts\python.exe -m pip install -r requirements-knowledge.lock
```

`setup.ps1` 是统一的环境准备入口，下载并核对固定Nexent源码、创建虚拟环境、安装依赖并准备私有目录。基础平台部署使用 `scripts/deploy.ps1`；它会创建私有配置并启动Docker服务，默认进行平台健康检查、停在账号操作前，不要求历史本地Qwen对照模型。仅在选择历史本地模型验收时，另行安装Ollama及Qwen3基础模型，并按 `models/Modelfile.4b`、`models/Modelfile.8b` 和 `scripts/configure_ollama.ps1` 配置两个固定别名；部署检查显式添加 `-RequireLocalModels`，独立检查使用 `check_native_ready.py --require-local-models`。`download_models.py` 是另行执行的较大权重下载辅助入口；包内没有权重。账号初始化入口 `scripts/initialize_accounts.ps1` 及部署的 `-ProvisionAccounts` 仍保留双Qwen前提，供原技术基线使用；云端链需按独立导入路径重新绑定，不能把平台检查通过当作账号或模型已配置。不要直接在生产目录执行，不要带 `-ProvisionAccounts` 跳过预定的账号接手步骤。

若需 MinIO 源码构建，`deploy.ps1 -BuildMinioFromSource` 会从已固定的官方源码构建；相关许可和网络资源仍需另行取得。模型配置、连通检查、模型调用分别验收，模型连通性检查也可能产生供应商请求。本说明不授权额外付费或云端运行。

云端凭据只使用接收方已批准的环境变量，例如 `DEEPSEEK_API_KEY`，不得填写到公开 JSON、命令历史、截图或清单。云端 API 使用已有环境变量或系统代理并保留 HTTPS 证书校验；本机 `localhost`、Nexent、MCP 使用直连/`NO_PROXY`，不把代理地址写入源码。

在新环境按需运行下列合成契约检查，可验证本体、暂停、引用绑定和待审状态的工程规则；这些测试不访问真实官网、模型或原生 Agent，也不证明业务达标。已有环境无需为本次打包重复执行它们。


接收方必须针对**自己这次**候选的结构、来源摘要和预期 head 进行人工复核；本包中的确认记录只对应原来的候选，不能作为所有未来运行的通用授权。`confirm-demo` 要求候选 ID、预期 head、复核人和 `--confirmed`，演示后在 `finally` 中回退。业务发布和现行适用性需另行审批。
