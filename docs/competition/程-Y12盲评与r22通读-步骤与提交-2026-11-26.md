## 二、任务一：Y12 盲评

### 1. 核对材料

进入 `review-packs/Y5-Y12-v40-20261126/`，先确认材料没被改过：

```bash
sha256sum -c SHA256SUMS        # 三行都应显示 OK
```

Windows 上没有 `sha256sum` 时，用 Git Bash 执行，或者跳过这一步，交回时由队长核对。

| 文件 | 用途 |
| --- | --- |
| `README.md` | 本轮规则和交回方式（与本文一致） |
| `review.md` | 阅读材料：每题的问题、参考要点、三份输出、所引原文全文 |
| `sheet-程.csv` | **你的评分表**，只改这一张 |

### 2. 读评审说明

打开 `review.md`，先读开头的“评审说明”表格。各列的取值如下（与表格一致）：

| 列 | 可填的值 | 什么时候填什么 |
| --- | --- | --- |
| `conclusions_correct` 保留的结论是否正确 | 是 / 否 / 部分 / 不适用 | 对照原文和参考要点；**输出是停止时填“不适用”** |
| `missing_points` 是否漏掉必答要点 | 否 / 漏次要 / 漏核心 / 不适用 | 漏核心指问题要问的主要内容没答到；停止时填“不适用” |
| `citations_support` 引文是否支持结论里的条件和限定语 | 是 / 否 / 不适用 | 重点看“有条件”“仅限”“除外”、日期、数字、单位；停止时填“不适用” |
| `excerpt_relevant` 以“原文摘录：”开头的条目是否相关 | 是 / 否 / 无摘录 | 只看以“原文摘录：”开头的条目；**没有这类条目就填“无摘录”**，这是多数情况 |
| `stop_judgment` 停止是否合理 | 合理 / 不合理 / 待确认 / 不适用 | 只判断停止的输出：按参考这题该停填“合理”，该答却停了填“不合理”；**答复的输出填“不适用”** |
| `reference_issue` 参考答案是否有误 | 未发现 / 有误 / 待确认 | 判断题目下方的参考答案本身；**同一题三行填相同的值**；“有误”时在 `remark` 写原因，评分仍按原文事实 |
| `remark` 备注 | 自由文字 | “有误”时必填原因，其他情况可空 |

`question_id`、`label`、`reviewer` 三列已经填好，**不要改**。

### 3. 逐题评分

从 Y01 开始，一题一题来。每题：

1. 读问题和必答要点；
2. 依次读输出 A、B、C，每条结论都对照它下面的引文和“引用的原文单元（全文）”；
3. 在表里填这一题的三行。

输出里偶尔有“部分答复”“原文摘录”等字样，可能暗示它来自哪种方法。**不要据此猜方法，也不要因此加分或减分。**

建议评完 6 题保存一次。

### 4. 交回前自查

| 检查 | 要求 |
| --- | --- |
| 行数 | 36 行，Y01—Y12 各 A、B、C |
| 取值 | 每格都在第 2 步表格的取值内，没有空格（`remark` 除外） |
| 停止的输出 | 前三列填“不适用”，`stop_judgment` 填合理、不合理或待确认 |
| 答复的输出 | 前三列不能填“不适用”，`stop_judgment` 填“不适用” |
| 原文摘录 | 有以“原文摘录：”开头的条目，才能填是或否；没有就填“无摘录” |
| 参考答案 | 同一题三行的 `reference_issue` 相同；“有误”的都写了原因 |
| 编码 | 用记事本打开，中文正常显示 |

### 5. 提交盲评表

在私密仓库根目录：

```bash
git switch -c review/cheng
git add review-packs/Y5-Y12-v40-20261126/sheet-程.csv
git status --short          # 只应看到这一个文件
git commit -m "Y5 review: cheng"
git push -u origin review/cheng
```

不改 `review.md`、不改另一张表、不合并到 main。推送后告诉队长。队长运行格式检查：

- 有问题会把行号和原因发回给你，由你本人修改后再推，**队长不代改**；
- 两张表都通过后，队长揭盲并统计。

### 2. 重点看什么

1. **事实与数字**：每个数字能在材料里找到出处，前后一致。
2. **口径**：对照公开仓库 [已知局限与材料表述边界（V4.0）](已知局限与材料表述边界-V4.0-2026-11-26.md) 的“不能写”一列。常见越界有：
   - 把开发对比写成“独立评测”“准确率提高”；
   - 回避 30 题盲评原结论（43/60，普通检索 51/60）；
   - 把 Jev 当成人工评分；
   - 其他各条以局限表为准（盲评交回后再打开）。
3. **版本**：除标明“历史”“V3.1”的段落外，不应有把 V3.1 写成当前版本的句子。
4. **截图**：不能露出账号、手机号、邮箱或本机路径。
5. **可读性**：评委第一次读能否看懂，哪句太绕、哪个术语没解释。

封面团队合照一格是“待补”，由队长处理，不用记。

你负责过规范条款映射和扫描件复核，**附录第 3、5、6 章**里涉及来源定位、版本和扫描转录的说法请重点看。

### 3. 写意见表

在 `materials-r22/` 新建 `通读意见-程.csv`（CSV UTF-8），一条意见一行：

```
文件,页码,原文（摘一句即可）,问题类型,建议改法
技术附录,52,"……",数字不一致,改为……
```

问题类型只用这六种：事实错误、数字不一致、口径越界、版本过时、隐私、表述不清。

没有意见也要交一份只有表头的表。

### 4. 提交意见表

```bash

git switch -c readthrough/cheng
git add "materials-r22/通读意见-程.csv"
git status --short          # 只应看到这一个文件
git commit -m "r22 readthrough: cheng"

```

## 五、常见问题

| 现象 | 处理 |
| --- | --- |
| 用 Excel 打开 CSV 中文乱码 | WPS 直接打开；Excel 用“数据 → 从文本/CSV”导入，编码选 UTF-8 |
| 保存后中文变乱码 | 另存时选“CSV UTF-8（逗号分隔）”，不要选普通“CSV” |
| 某题拿不准 | `stop_judgment`、`reference_issue` 可以填“待确认”，在 `remark` 写原因；前四列按你的最好判断填 |
| 觉得参考答案错了 | `reference_issue` 填“有误”，`remark` 写原因和原文位置；评分按原文事实，不按参考 |
| 不小心看到了 Y12 结果或局限表 | 照实告诉队长，在盲评表的提交说明里注明；不要因此重评 |
| 推送被拒 | 先 `git pull`，确认没有改到别的文件；仍不行就私下发文件给队长 |
