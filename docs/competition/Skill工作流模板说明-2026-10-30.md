# Skill 工作流模板说明

编制日期：2026-10-30（Asia/Shanghai）。对应第三题"Skill 分层编排""可复用 Skill 工作流模板沉淀"。本文说明从南京、河南两条已实跑链路中提炼出的模板，以及部署新 profile 的步骤。**模板本身没有在 Nexent 上部署新 profile，也没有发起模型调用**；部署计时由李嘉杰试用后填写。

## 分层结构

| 层 | 内容 | 是否模板化 |
| --- | --- | --- |
| 平台层 | Nexent 主控 + 检索、核验两个子 Agent；温度 0、非思考、每步 1024 tokens；草稿禁用、不发布 | 由 `provision_ontology_crossdoc_native.py` 统一创建，profile 只换名称和显示前缀 |
| 编排层 | Skill：固定"读 Skill→开任务→检索子 Agent→核验子 Agent→读状态→完成"五步与停止规则 | 是：[SKILL.template.md](../../config/skill-templates/reviewed-ontology-workflow/SKILL.template.md) |
| 协议层 | 主控 duty prompt：可执行动作格式、子 Agent 调用示例、禁止重复与重试 | 是：[PROTOCOL.template.txt](../../config/skill-templates/reviewed-ontology-workflow/PROTOCOL.template.txt) |
| 工具层 | 5 个 MCP 工具 `govkb_ontology_crossdoc_open_query/retrieve/verify/state/finalize`，每步都检查来源门、已确认版本、实现指纹和来源绑定 | 共用一个服务；`open_preview` 按 `ontology-binding.json` 的 profile 分派 |
| 执行层 | 来源适配器、已人工确认的本体依赖计划、领域算子 | **否**：每个 profile 仍需代码，河南见 `henan_multimodal*.py` |

一个 profile 只需填写：情境 ID、三个 Agent 名、显示前缀、Skill 标题与说明、检索/核验两步的保全要求、证据说明、输出不变量、主控协议的领域说明，以及实现指纹函数。

## 已验证结果

- 用[河南规格](../../config/skill-templates/profiles/henan-multimodal.json)渲染，得到的 Skill 与 10-22 实跑验收的 `govkb-henan-multimodal-preview/SKILL.md` 逐字一致，主控协议也与当时接线所用的 `PROTOCOL` 逐字一致。
- 用[南京规格](../../config/skill-templates/profiles/nanjing-ontology-crossdoc.json)渲染，主控协议与南京接线逐字一致。南京旧 Skill 早于模板、文字不同，渲染工具判定为 `differs` 并拒绝覆盖。
- 通用接线工厂 `workflow_template.profile_provisioner` 用河南规格生成的接线模块，与河南专用加载器的名称、端口、服务、工具、角色工具、协议和第一步动作完全相同，共享模块的全局变量保持不变。
- 用一个虚构的北京 profile 演示新渲染：生成的 Skill 写入独立目录，不残留占位符或河南情境；重复渲染结果为 `unchanged`。
- [示例规格](../../config/skill-templates/profiles/example-new-profile.json)中的 `TODO` 未填完时会被拒绝；非法名称、路径穿越、任意模块指纹、重复的 Agent 名、缺失或多行的槽位都会在渲染前被拦下。
- 定向测试 `tests/test_workflow_template.py` 14 项通过，并与河南、南京两组接线测试一起共 63 项通过。没有运行全仓回归。

## 部署新 profile 的步骤

```powershell
Copy-Item config\skill-templates\profiles\example-new-profile.json config\skill-templates\profiles\<新名称>.json
# 填完所有 TODO 后：
.\.venv\Scripts\python.exe scripts\workflow_template.py check --profile config\skill-templates\profiles\<新名称>.json
.\.venv\Scripts\python.exe scripts\workflow_template.py render --profile config\skill-templates\profiles\<新名称>.json
```

1. **填写规格**：复制示例规格并填完全部 `TODO`。`admission` 第一行以冒号或句号开头，接在固定句"is admitted"之后；检索、核验两步的第一行接在"exactly once."之后，后续行会自动缩进。
2. **检查与渲染**：`check` 只读校验；`render` 把 Skill 写到 `config/skills/<skill_name>/SKILL.md`，已有且内容不同的 Skill 一律不覆盖。
3. **执行层（需要代码）**：在 `ontology_crossdoc_preview_server.open_preview` 中登记新 profile，并提供来源适配器、候选构建和依赖计划算子，写法参考河南的 `henan_multimodal.py`、`henan_multimodal_sources.py`、`henan_multimodal_preview.py`。规格中的 `fingerprints` 指向新模块的实现指纹函数。
4. **候选与确认**：准备真实来源候选，经人工结构确认后在隔离库激活；结构确认不等于业务批准。
5. **接线与运行**：用 `profile_provisioner(规格, runtime, output)` 生成接线模块并执行其已有检查；原生运行需要单独授权、预算和来源核对。

## 边界

- 模板目前只覆盖"已确认本体 + 主控/检索/核验三角色"这一类查询流程。河南新旧资料的更新流程（整理/核验子 Agent）和更早的南京三跳链尚未纳入。
- 第 3 步仍需开发，部署新事项不是纯配置；可以快速复用的是编排层、协议层、平台层和工具层。
- 模板化不改变暂停、unknown、未批准、未发布等任何门槛；渲染出的 Skill 不构成业务结论。
