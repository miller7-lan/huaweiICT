## 接口定稿时必须闭合的四个缺口

现有七个拟议 MCP 工具使用 `task_id` 或 `handoff_id`，但没有定义这些对象的全部页面操作入口。建议由受信工作台 HTTP API 负责下列操作，保留 MCP 业务工具分工；路径、类型和错误码须在实现前形成独立契约稿。

| 缺口 | 需要定稿的行为 | 必验场景 |
| --- | --- | --- |
| 任务从何产生 | 创建时确认事项范围并绑定已发布快照；不接受客户端自行指定租户、所有者或任意版本。未确认事项/未发布快照时明确阻断。 | 无快照、未知范围、伪造所有者/版本；任务读取与创建回包一致。 |
| 材料如何保存 | 对每条规则记录存在/缺失/未知及输入来源；材料声明与人工核验状态分别保存。明确允许更新的任务阶段和并发修订检查。 | 缺一项、未知条件、择一材料、共享材料、旧修订覆盖新修订。 |
| 工作人员如何接单 | 按服务端授权返回交接列表与详情；明确首次受理、重复打开、补材料后查看哪个修订以及越权对象的返回行为。 | 本人/他人任务、跨租户、无授权受理范围、旧交接仍可追溯。 |
| 谁完成最终确认 | 工作人员显式操作，服务端绑定实际核验结果、交接修订、知识版本及结果指纹；保存确认人和时间。补材料后旧确认不得表示新结果已确认。 | 确认前后、重复确认、过期修订确认、确认后补材料、模型冒充人工确认。 |

材料规则还需固定条件求值的三种结果：满足、不满足、未知。对条件不明的材料显示未知，不把它算成明确缺失；必交、条件交、择一、共享获取分别给出可执行例子。业务标准由经复核原文确定。

交接幂等建议以实际租户、主体、任务和操作为作用域，并在服务端对规范化内容计算指纹。同键同内容返回原交接，同键不同内容返回冲突；验收应覆盖并发双击与技术重试。此处是待定稿工程方案，没有新增业务事实。
