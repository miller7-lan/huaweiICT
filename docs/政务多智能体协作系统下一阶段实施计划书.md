编制日期：2026年10月12日　适用对象：项目团队　版本：1.0

## 一 阶段目标与当前基线

我们先补齐 BT01 至 BT16 空白验收，再由团队选定一个地区和一个事项，接入有来源的资料，完成群众引导、工作人员材料核验与知识版本追踪，形成比赛演示和提交材料。

现有结果只证明空库技术链路，不代表业务正确率或全部赛题要求已满足。

| 基线项目 | 已取得的本机证据 |
| --- | --- |
| 平台和部署 | Nexent v2.7.0 固定提交，Docker Desktop 与 Ollama 已部署 |
| Agent 和工具 | 主 Agent、群众 Agent、工作人员 Agent；现有 MCP 仅有三个工具 |
| 测试与对照 | 92 项基础测试、SSE 6 次调用通过；两模型各 20 次，合计 40/40 |

本计划的执行顺序已经确定。试点地区、具体事项、团队成员安排和赛事截止时间，在相应阶段核定后登记；以下四周排期是资源估算，不代表已确认的比赛期限。

## 二 基础验收覆盖与补齐任务

原策划书的 BT 编号尚未逐项形成完整验收记录。下表说明现有证据能复用到哪里，以及还需要补什么；“可复用”不等于该 BT 用例已经正式判定通过。

| 编号 | 原策划书目标 | 当前覆盖情况 | 下一步动作 |
| --- | --- | --- | --- |
| BT01 | 群众首次入口为空状态 | 已有群众登录和问答截图，但账号已有技术会话 | 使用没有历史会话的新隔离账号；验证入口无默认业务案例 |
| BT02 | 空输入不调用模型或工具 | 网页发送按钮禁用可观察；缺少独立编号证据 | 记录空输入提示、按钮状态及前后模型和工具调用计数 |
| BT03 | 群众请求只进入群众 Agent | 40 次对照中有真实身份、路由、SSE 和审计 | 按 BT03 归档一次新会话及其工具顺序 |
| BT04 | 工作人员空工作台与空待办 | 已验证工作人员问答，尚未验证事项工作台 | 实现或明确独立事项工作台入口，展示空待办并记录证据 |
| BT05 | 角色不明确时停止 | 未映射身份返回 ROLE_NOT_CONFIGURED；缺少完整入口证据 | 检查应用层和工具层停止；入口选择不得授予工作人员权限 |
| BT06 | 空知识检索返回空记录和引用 | search_evidence 已返回 EMPTY 和 NO_KNOWLEDGE | 复用工具与原生会话证据，登记零记录及空引用 |
| BT07 | 空图谱不生成节点或关系 | query_knowledge_graph 尚未实现 | 在隔离扩展服务中实现空图谱查询和未连接状态 |
| BT08 | 缺少事项材料时阻断核验 | 工作人员真实会话返回缺少事项、材料、证据 | 归档 BLOCKED、缺失项与无审批结论的实际结果 |

角色来自登录会话和受控映射。群众选择工作人员页面只能改变导航，不能改变工具权限；未配置角色应停止并要求管理员核实。

每项验收至少记录编号、前提、实际操作、真实结果、判定和证据路径。界面行为必须保留界面证据；API 验证不能替代页面入口验证。

## 三 更新和异常验收补齐任务

现有服务对业务库非空会主动报错，且原生验收固定只允许三个工具。因此，新增图谱与更新能力应放在隔离扩展环境，原有空库服务和历史证据继续保留。

| 编号 | 原策划书目标 | 当前覆盖情况 | 下一步动作 |
| --- | --- | --- | --- |
| BT09 | 无新文件时没有知识更新 | prepare_update 尚未实现 | 无输入返回明确空状态；不创建候选版本或知识版本 |
| BT10 | 无候选变更时拒绝发布 | publish_update 尚未实现 | 校验候选、权限和确认前提；缺失时 BLOCKED，版本数不变 |
| BT11 | 群众不能维护知识 | 已验证群众调用工作人员工具被拒绝；维护接口未验证 | 对图谱及更新维护接口分别做真实越权测试 |
| BT12 | 工具超时后有限重试停止 | SSE 超时及原生存储锁验证已通过 | 按编号归档尝试次数、ERROR、停止原因和恢复结果 |
| BT13 | 缺失连接配置不能显示成功 | 部分单元检查及连接中断已覆盖，缺配置页面尚未验证 | 在隔离实例撤除配置；验证未配置提示，不改正常运行实例 |
| BT14 | 重复空更新没有副作用 | 现有重复用例是检索，不是更新 | 对同一空更新请求连续执行，核对候选、版本、事项数量不变 |
| BT15 | EMPTY 后停止业务推理 | 正式对照有停止、空引用和无额外工具的证据 | 按编号归档子 Agent 结束与主 Agent 最终结果 |
| BT16 | 前端和日志中的角色与停止原因一致 | 三账号 UI、SSE、审计及凭据检查可复用 | 形成统一编号记录；开发临时调试以 request_id 关联，不编造会话 ID |

BT09 若使用 NO_CHANGES，须注明它仅表示本次没有可处理输入，不能解释成已经检查所有外部政策且确认无变化。工具异常也不能被解释成业务条件不满足。

第一阶段完成条件是 16 项都已实际执行、符合各自预期并有可复核证据。缺实现、缺页面或配置未就绪，应记录未执行或受阻，不算该阶段完成；不能用相关单元测试代替尚未执行的整项验收。

## 四 下一阶段架构与业务范围

### 保留基线并建立隔离扩展环境

现有空库服务继续使用原三工具、原 Agent 配置和原数据库。扩展环境使用独立数据库、知识索引、账号配置和证据目录；不得直接向当前空库写入业务内容。新增配置和凭据同样保存在受控私有目录，仓库仅保存可复现代码与脱敏说明。

建议新增独立 MCP 实例，默认使用本机 8766 端口，实施前检查占用。新增工具采用独立 govx 前缀，避免与原工具重名；Agent 导入包也使用独立名称。现有 SDK 错误覆盖仅匹配原 MCP 地址，新地址需单独验证成功链路、超时与连接失败的真实行为。

| 扩展能力 | 最小实现与约束 |
| --- | --- |
| 环境与身份检查 | 接收平台注入的真实身份，返回角色、配置状态和所用知识版本 |
| 证据检索 | 按可见范围和任务固定版本检索，返回原文、来源、页码或段落位置 |
| 图谱查询 | 第一版可使用关系表表达原策划书七类对象及关联，所有边都能追溯来源 |
| 材料前提核验 | 检查事项、材料、证据是否齐备；缺失时列明缺项，保留人工确认环节 |
| 更新准备 | 提取候选变化与影响范围；无输入和解析失败均不能产生已发布版本 |
| 知识发布 | 由独立知识维护权限和人工确认控制，发布后保留旧快照与复核记录 |

新接口延续 status、items、citations、knowledge_version、message_code、data 这些结果字段。业务扩展可以新增来源定位和版本信息，现有空库接口保持原契约。

### 单事项业务演示

团队在第二阶段核定一个地区和一个事项，优先选择官方资料易核验、材料清单较短、能体现双方协作的事项。记录事项编码、办理部门、资料 URL、适用范围、有效时间、文件指纹和使用权限。未确认的资料进入待复核状态。

最小流程为：群众问题进入主 Agent，群众 Agent 检索证据并生成办事引导；需要交接时保存事项上下文，工作人员 Agent 检查材料齐备性并列明证据差异。建议固定同一知识快照，交接记录保留来源和版本；最终业务处理意见由工作人员确认。

首版不接入真实审批、资金发放或消息发送。多模态 OCR 和更多行业迁移在文字资料闭环稳定后评估；没有实现与数据时不申报相关效果。

### 工作角色与责任产物

| 工作角色 | 主要职责 | 责任产物 |
| --- | --- | --- |
| 需求与资料负责人 | 核对赛题、选定事项、确认来源与人工标准答案 | 需求对应表、来源登记、复核记录 |
| MCP 与知识负责人 | 实现受控工具、关系结构、版本和影响分析 | 服务代码、迁移说明、工具测试与审计 |

一人可以兼任多个工作角色。知识发布确认、标准答案复核和关键业务结果复核应尽量由不同人员完成；成员姓名和投入时间在 T0 登记，不虚构分工。

先将本机修复形成可审阅的变更与证据索引。远程推送、PR 合并和正式提交由团队明确授权后执行；当前已有未提交修改必须保留。

## 六 验收标准与交付清单

技术验收沿用真实执行证据，业务验收另建人工复核的标准答案。按资料来源或案例组划分开发集与验收集，避免同一案例改写后跨入两个集合。

| 验证内容 | 项目内目标或判定方法 |
| --- | --- |
| 空白验收与原回归 | BT01 至 BT16 实际完成；原有自动测试保持通过，空库仍为零记录 |
| 引用正确性 | 用留出样本核对引用是否支持对应说法，首版目标不低于 95% |
| 材料缺失识别 | 以人工复核缺项为准，首版召回率目标不低于 95%；同时报告误报 |
| 角色权限 | 所有越权、身份冒用、非法发布用例均被应用层或工具层阻断 |
| 版本一致性 | 同一任务固定知识快照；更新后新任务采用新版本，历史结果保留原版 |
| 变更影响分析 | 对真实可核验的版本差异同时报告精确率、召回率与复核耗时 |
| 性能与资源 | 在本机记录预热后耗时、失败率、内存和实际模型加载，不套用其他机器结果 |

上述百分比是建议的项目内部验收目标，不是已证实的业务效果，也不是官方评分线。首轮建议准备不少于 30 个经复核的留出任务，覆盖材料齐备、缺项、证据不足、来源冲突、版本变化和越权；样本不足时报告分母与局限。

对照设置为普通文档检索问答、单 Agent 工具调用、三 Agent 协作。保持模型、资料、任务及资源限制一致，并记录提示词和工具差异。知识更新另比较全量重建与增量处理，报告人工修订时间和残留错误。

| 交付材料 | 内容要求 |
| --- | --- |
| 需求与技术方案 | 赛题对应、架构、Agent 职责、工具契约和版本一致性设计 |
| 可运行工程 | 服务代码、锁定依赖、配置模板、部署脚本和隔离环境说明 |
| Agent 与 Skills | 实际导出并验证可导入的配置；可复用步骤、权限及停止条件 |
| 数据和评测说明 | 来源、授权、适用范围、处理记录、划分方法、标准答案与指标分母 |
| 验收和演示材料 | BT 编号证据、真实问答截图、业务演示录屏与异常恢复记录 |
| 正式开发设计文档 | 按赛事模板补齐栏目，将已完成事实与下一阶段计划分开陈述 |

没有两版真实资料时，只交付版本接口和工程验证，不宣称政策影响识别准确率。案例、政策条件、金额或申请人事实均不得由模型补齐成测试业务事实。

## 七 持续推进目标与执行边界

Codex Goals 可以让同一聊天围绕一个有完成标准的目标跨轮次继续工作。计划模式用于确定方案，目标模式用于持续执行和检查完成条件；定时自动化适合周期检查。目标仍受暂停、阻塞、使用预算与运行环境约束。

建议先把 M1 设为一个独立目标。其范围明确、资料前提少，也能保留已经验证过的技术基线；M2 的真实资料接入须等团队核定地区、事项和使用范围。

推荐目标文本为：

完成原策划书 BT01 至 BT16 的空白技术验收实施。保留现有三工具空库服务与原有测试，通过隔离扩展环境补齐空图谱、无输入更新、发布前提与幂等性。不得导入或虚构政策、材料和案例。每项保存真实界面、工具与审计证据，更新覆盖矩阵和复现说明。目标完成需 16 项实际执行并全部符合预期、原回归保持通过、业务库为空且凭据未进入仓库；受阻或未执行不算完成。需要人工操作或正式材料时，报告具体阻塞与所需输入；未经授权不推送、合并或正式提交。

启动可使用 `/goal` 加上述目标；查看用 `/goal`，暂停用 `/goal pause`，恢复用 `/goal resume`，清除用 `/goal clear`。本计划书只给出建议目标，未启动持续执行，也未配置定时自动化。

实施过程中持续维护进度文件：已完成动作、验证证据、下一步和阻塞项。某次模型输出看似合理，不能替代真实工具调用；阶段结果必须由可复核的事实判定。
